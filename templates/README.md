# 작업 입출력 양식

작업을 맡기는 입력과 담당자가 돌려주는 결과를 연결하는 권장 양식이다. 개발, 조사, 설계 검토, 글쓰기에 같은 항목을 사용하고 필요한 부분만 확장한다. 실제 기록은 사용자가 지정한 보관 위치 또는 승인된 프로젝트 환경에 작성한다. 이 저장소에는 빈 양식과 가상 예시만 둔다.

| 파일 | 작성 주체와 용도 |
| --- | --- |
| [task-input.md](task-input.md) | 사용자 또는 조율자가 한 담당자에게 전달하는 작업 |
| [task-result.md](task-result.md) | 담당자가 제출하는 산출물·검증·미해결 사항 |
| [task-report.md](task-report.md) | 조율자가 여러 작업을 종합하는 선택적 보고서 |
| [가상 예시](../examples/task-contract.md) | 개발과 글쓰기 작업의 입력·결과 연결 |

## 최소 계약

| 구분 | 필수 항목 | 기준 |
| --- | --- | --- |
| 입력 | `task_id`, `role`, `goal`, `scope`, `acceptance` | 한 작업의 책임과 완료 조건을 식별한다. |
| 결과 | `task_id`, `status`, `summary`, `artifacts`, `checks`, `remaining`, `usage` | 동일한 작업 ID를 사용하고, 모든 완료 기준의 판정과 근거를 남긴다. |

- 작은 작업은 완료 기준 하나와 짧은 결과면 충분하다. 선택 항목은 필요할 때만 남긴다. `artifacts`, `remaining`이 없으면 `없음`을, 사용량을 모르면 `unavailable`을 명시한다.
- `role`에는 실행 설정의 역할 ID를 사용한다. 기본값은 `coordinator`, `architect`, `designer`, `backend`, `frontend`, `verifier`다. 역할은 기술 조사·글쓰기 같은 작업 유형과 별개이며 실제로 맡을 수 있는 역할을 선택한다.
- `scope`에는 포함·제외 범위를 쓴다. 파일을 수정하면 대상 경로도 명시하고, 조사·검토라면 읽을 자료와 결과물 범위를 적는다. 프로젝트 경로의 기준은 대상 프로젝트 루트이며 외부 자료는 별도 출처를 표시한다.
- `acceptance`의 `AC-01` 같은 ID를 결과의 `checks`에서 그대로 사용한다. 검증 방법을 실행할 수 없으면 그 기준을 `unverified`로 남긴다. 원래 기준을 바꾸어 통과 처리하지 않는다. 범위 변경이 합의되면 입력을 갱신하고 결과에도 변경 사실을 남긴다.
- 선택적 추가 확인은 시작할 때 `additional_checks`로 분리하고 미수행 이유를 남긴다. 필수 완료 기준의 실패·미검증을 이 항목으로 옮겨 완료 처리하지 않는다.
- 작업에 필요한 자료의 관련 부분과 참조만 전달한다. 조건, 예외, 원래 요구사항과 검증 근거가 빠지지 않도록 확인하고, 더 자세한 자료가 필요하면 허용 범위에서 확인한다. 전체 대화와 내부 추론을 복사하지 않는다.

## 결과 상태

| `status` | 의미 |
| --- | --- |
| `completed` | 이 작업의 모든 완료 기준이 `pass`이고 필요한 산출물이 제공되었다. 전체 업무나 통합 검증의 완료를 뜻하지 않는다. |
| `partial` | 일부 작업을 수행했지만 실패·미검증·미완료 항목이 남았다. 남은 작업과 다음 조치를 적는다. |
| `blocked` | 필요한 결정·자료·권한·선행 작업 등이 없어 허용된 범위에서 더 진행할 수 없다. 해소에 필요한 조건과 담당자를 적는다. 기존 산출물이 있을 수도 있다. |

`checks`는 `pass`(통과), `fail`(실패), `unverified`(미검증)를 사용한다. 실패에는 기대 결과·실제 결과와 재현 또는 확인 방법을, 미검증에는 이유를 남긴다. 가능한 경우 확인한 산출물의 버전·변경 범위와 명령·출처 등 근거를 연결한다. 판정 주체는 작성자의 자체 검증인지 별도 검증자인지 표시한다. [실행 기록](../runtime/execution-records.md)을 활성화하면 실행 오류·중단·시간 초과도 별도로 남긴다. 실행 성공이나 결과 유무로 업무 완료를 추정하지 않는다.

## 상황에 따라 추가할 항목

| 위치 | 항목 | 사용할 때 |
| --- | --- | --- |
| 입력 | `parent_task_id`, `task_type`, `depends_on` | 작업을 분리하거나 선행 작업의 필요한 결과·상태를 전달할 때 |
| 입력 | `context`, `constraints`, `deliverables` | 관련 자료, 기술·디자인 제약, 산출물 형태를 전달할 때 |
| 입력 | `execution_permissions` | [권한 인계 양식](execution-permissions.md)으로 허용 범위·유효 설정·준비 근거와 미해결 권한을 전달할 때. 자동 권한 설정은 아님 |
| 입력 | `escalation` | 계약 변경 등 담당 범위를 벗어나는 판단의 인계 조건을 정할 때 |
| 입력 | `budget` | 예상 범위·배정 예산·중단 조건이 정해졌을 때 |
| 결과 | `decisions` | 대안 사이의 중요한 선택이 있었을 때 |
| 결과 | `blocker` | `blocked`일 때 필수: 원인·시도한 내용·해결에 필요한 조치와 담당자를 전달 |
| 결과 | `concerns` | 미해결 위험이나 완료를 막지 않는 개선 의견이 있을 때 |
| 결과 | `handoff` | 다른 역할의 후속 작업이 필요할 때 |
| 결과 | `improvement` | 반복 실패나 비용 증가를 바탕으로 개선을 제안할 때 |

의존 작업은 필요한 결과와 상태를 확인한 뒤 인계한다. 실패·미검증·변경된 계약을 숨긴 채 다음 작업으로 넘기지 않는다. 검증자에게는 원래 입력, 실제 변경 범위, 산출물 버전과 기존 결과를 함께 전달한다. 증거가 확인한 버전 이후에 산출물이 바뀌면 그 증거가 여전히 유효한지 확인한다. 완료 기준에 영향을 주는 위험은 `concerns`에만 묻지 말고 해당 `checks`와 `remaining`에도 반영한다.

`blocked`의 원인은 정보 부족, 선행 작업, 권한·환경, 범위·설계 충돌, 예산 등으로 짧게 구분할 수 있다. 확인한 내용과 필요한 조치를 함께 전달하고, 같은 요청을 조건 변경 없이 반복하지 않는다. 조율자는 허용된 범위에서 정보 보완·재분할·재계획을 진행하고, 외부 결정이 필요한 경우에만 사용자에게 확인한다.

## 자료 탐색과 전달

- 먼저 작업 목표와 관련된 파일·심볼·오류를 찾고 해당 부분부터 읽는다. 검색 결과에 근거가 부족하거나 주변 맥락이 필요하면 읽는 범위를 넓힌다. 설정·호출 관계·실패 조건과 같이 판단에 필요한 내용은 생략하지 않는다.
- 긴 코드·로그를 매번 통째로 전달하지 않고, 관련 구간·오류와 원본 참조를 사용한다. 로그가 잘렸거나 원본을 확인할 수 없으면 그 한계를 밝힌다. 작업에 필요하고 허용된 자료만 접근하며 비공개 내용은 [개인정보 관리 기준](../principles/privacy.md)을 따른다.
- 인계에는 목표·완료 기준·확정된 계약·관련 자료·남은 문제를 포함한다. 검증자는 요약에 더해 원래 요구사항과 해당 변경본·증거를 확인한다. 작은 작업은 필요한 내용만 간결히 작성한다.
- `context`에는 먼저 볼 위치뿐 아니라 필요한 이유와 확인한 범위를 전달한다. 확인한 사실과 추정·미확인을 구분하고, 완료 기준과 적용되는 공통·프로젝트 제약을 빠뜨리지 않는다. 다음 담당자는 이를 출발점으로 삼고 필요하면 허용 범위에서 추가 탐색한다.
- 참조는 다음 담당자가 접근할 수 있어야 한다. 파일·함수명은 프로젝트 기준 상대 위치로, 줄 번호는 참고 위치로 제공한다. 기준 커밋이 있더라도 미커밋 변경을 포함할 수 있으므로 관련 변경의 존재와 범위를 함께 밝힌다. 문서·웹 자료는 확인한 버전이나 시점을 적고, 변경됐다면 인계 정보를 갱신한다. 접근할 수 없다면 미확인으로 알리고 필요한 자료를 요청한다. 민감한 자료와 경로는 승인된 범위에서만 전달한다.
- 서로 다른 작업 폴더를 쓰는 역할에는 프로젝트 루트와 외부 입력의 절대 경로를 전달한다. 출력은 다음 담당자에게 허용된 폴더를 사용하고 반환 시 절대 경로를 알린다. 같은 host의 명시 입력은 [인계 준비 도구](../runtime/harness.md)로 존재·해시를 확인할 수 있다. 원격 접근 가능 여부까지 확인하는 도구는 아니다.
- 이 기준은 작업 지침이다. 실행기가 검색·인계 범위를 자동 선택하거나 읽은 내용을 추적한다는 뜻은 아니다.

## 예산과 사용량

- 입력의 예상 사용량은 범위·근거·불확실성을 함께 기록한다. 예상치와 허용 한도를 구분하며, 근거가 없으면 미정으로 둔다. 모든 작업에 동일한 숫자를 기본값으로 넣지 않는다.
- 결과의 `usage`는 `measured`, `partial`, `unavailable` 중 하나다. 실제 수치는 실행 도구의 기록과 측정 출처가 있을 때만 사용한다. 미측정은 0이 아니며 역할별 배분을 임의로 계산하지 않는다.
- 측정했다면 작업·시도·세션 식별자, 측정 범위, 입력·출력 토큰과 집계 기준을 남긴다. 캐시·추론 값이 입력·출력의 부분 집합이면 더하지 않는다. 실제 모델·effort와 시간도 확인 가능한 실행 기록을 기준으로 적는다.
- 작업 여러 개가 같은 세션 측정값을 공유하면 각 결과는 같은 기록을 참조한다. 전체 보고서는 중복을 제거하고 조율·재시도·검증·보고·개선 비용도 포함한다. 보고 작성 종료 전 집계라면 포함되지 않은 범위를 표시한다.
- 모델·effort·sandbox는 실행 프로필에서 관리한다. 작업 입력에 적은 값만으로 실행 설정이나 권한이 바뀌지는 않는다.

## 개선 전후 비교

대표 작업의 동일한 목표·완료 기준과 검증 방법을 유지하고, 가능하면 같은 기준 변경본·환경에서 비교한다. 모델·effort·설정·지침 버전과 캐시 상태 등 비교에 영향을 줄 수 있는 차이를 기록한다. 확인할 수 없는 조건은 미상으로 둔다.

작업 수행과 조율·재시도·검증·보고, 필요한 개선 작업까지 측정 가능한 범위를 함께 보고한다. 입력·출력·캐시 사용량과 경과 시간뿐 아니라 완료 기준·미검증·재작업을 비교한다. 측정이 불완전하면 절감 효과를 단정하지 않는다. 토큰을 줄이기 위해 필요한 자료나 검증을 생략하지 않는다. 기록에 민감한 실행 내용이 포함되면 보관 위치와 공개 범위를 먼저 확인한다. 선택적으로 [작업 보고 양식](task-report.md)에 남길 수 있다.

## 현재 실행기에서 사용하기

현재는 Markdown 필드명을 맞추어 사용한다. 실행별 사용량 수집·선택적 저장·시간 제한과 저장된 기록의 집계를 제공한다. JSON 스키마에 의한 업무 입력·결과 검증, 자동 배정·인계, 누락된 사용량의 자동 수집·토큰 예산 강제는 후속 범위다. `scope`와 `budget`에 적은 내용은 작업 지침이며 실행기의 강제 제한이 아니다.

고정 개발자→검증자의 [단독 Codex 자동 조율 프로토타입](../runtime/orchestration-contract.md)과 스키마·가상 예제는 참고 자료로 보존한다. [환경 네이티브 연결 우선 결정](../runtime/architecture.md)에 따라 자체 엔진 구현은 보류했다. 공통 업무에는 이 Markdown 계약을 재사용하고, 실행·인계·수신 형식은 선택한 환경의 기능에 연결한다. 자동 변환·JSON 업무 검증 기능은 아직 없다.

기록과 양식을 연결하려면 `--task-id`, 선택적으로 `--parent-task-id`, `--task-type`에 입력과 같은 값을 전달한다. 비공개 저장 위치는 `--records-dir`, 별도 결과 보고서 참조는 `--result-ref`로 명시한다. Markdown을 자동 파싱하지 않으므로 일치 여부는 사용자가 확인한다. 실행 종료 후 기록의 `run_id`와 `usage`를 결과 양식에 참조할 수 있다.

`context`에 적은 파일은 자동으로 읽어 전달하지 않는다. 작은 자료는 `--context-file path/to/file:10:40`으로 명시해 함께 전달할 수 있다. `summary --records-dir ... --parent-task-id WORK-001`은 같은 상위 ID를 직접 가진 기록만 집계하며 하위 업무 관계를 재귀 탐색하지 않는다. 상세 조건은 [실행 기록](../runtime/execution-records.md)을 따른다.

입력 파일을 지정한 위치에 작성하고, 결과 양식도 함께 표준 입력으로 전달할 수 있다. 다음 명령은 `ai-workflow` 루트에서 실행하며 경로와 역할을 실제 값으로 바꾼다.

```sh
cat /path/to/selected/task-input.md templates/task-result.md |
  python3 scripts/workflow.py run --project ../my-project --role backend --task - --dry-run
```

`--role`은 입력의 `role`과 일치시킨다. 현재 실행기는 이 일치 여부나 양식 내용을 자동 검증하지 않는다. `--dry-run`은 실제 모델을 호출하지 않는다. 이를 제거하면 모델 사용량이 발생하며 결과는 터미널로 출력된다. 양식을 특정 폴더에 두는 것만으로 자동 적용되거나 저장되지는 않는다. 실제 기록을 저장할 위치와 공개 범위는 [개인정보 관리 기준](../principles/privacy.md)을 따른다.

- [완료 hook 가상 설정](completion-hook.config.json): 프로젝트별 비공개 ledger/DB/출력 경로 연결. 실제 activation·신뢰·지원 검증은 [완료 시 수집 가이드](../runtime/completion-hook.md)를 따른다.
