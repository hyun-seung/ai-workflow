# Orca IPC checkpoint 작업 입력

다음 승인된 worker 작업에 필요한 부분만 채워 비공개 spec에 넣는다. 양식 작성·전달은 worker 실행 허용이나 기술적 권한 부여가 아니다. 매 입력마다 주입하지 않는다.

## 조율자가 실행 전에 채울 것

- 업무와 실행 선택: <이번 요청의 근거 / 역할 / 사용자 선택 모델·effort>
- 실행 한도: <동시·누적 worker 수 / 새 배정 자동 재시도 수>
- 대상: <검증한 host·workspace / 현재 조율자 / 고정한 Orca CLI 절대 경로>
- 읽기·쓰기: <필수 지침과 입력 / 허용한 출력. 읽기 전용이면 코드·설정 수정 금지>
- IPC 업무 허용: <이번 worker의 checkpoint 질문 한 건과 필요한 상태 확인만. 불필요한 메시지·새 worker·다른 세션 조회 제외>
- 기술적 권한: <자식에게 노출된 실제 reviewer·approval policy·경계 또는 unknown. 부모 성공만으로 pass 금지>
- 정식 승인 요청 범위: <같은 checkpoint 명령의 승인 요청을 허용하는지 명시. 명시 거절·정책 부재는 차단. 새 배정/메시지 재전송 허용과 구분>
- 대기 후 조치: <조율자가 답해 이어 갈지 / 해당 worker 취소 시험인지. 취소라면 별도 명시 허용 범위>

미확인 권한을 확인됨으로 채우거나 새 세션 기본값을 임의로 변경하지 않는다. 다음 항목은 **동일 checkpoint의 정식 승인 요청을 업무 범위로 명시한 경우**의 worker 지침이다. 사용자가 모든 재시도를 금지했다면 그대로 붙이지 말고 그 차이를 먼저 정리한다.

## worker에게 전달할 짧은 지침

1. [IPC 요약](../runtime/orca-ipc-brief.md)과 작업에 지정된 필수 지침만 읽는다. 승인 방식·경계는 자기 실행 환경에 명시된 값만 보고하고 없으면 unknown으로 둔다.
2. 고정한 CLI·현재 host에서 이 배정의 조율자에게 checkpoint 질문 한 건만 보낸다. 필요한 IPC 차단이 이미 알려져 있다면 첫 전송부터 실행 도구의 정식 승인 경로로 그 정확한 명령을 요청한다. 예외 승인을 요청할 수 없다면 blocked로 종료한다.
3. 처음 확인한 `runtime_access_denied`로 접속 자체가 실패했고 전송되지 않았음이 확인된 경우, 위에 명시한 동일 명령의 정식 승인 요청 범위만 따른다. 이 양식을 근거로 자동 재전송하지 않는다. 검토 거절·timeout·접수 여부 미확인에는 다시 보내지 않는다.
4. 접수되면 영수증의 next에 따라 턴을 끝내 대기한다. 작업 입력이 취소 시험이면 준비 신호 후 추가 작업이나 완료 성공 보고를 하지 않는다.
5. 실패하면 오류·대상·실제 확인한 권한 수준만 보고한다. 다른 앱/CLI, 전역 권한 변경, 새 배정, polling으로 해결하지 않는다.

명령의 형태는 현재 설치 help로 확인한 뒤 채운다. 아래는 가상 표기이며 그대로 실행하는 명령이 아니다.

```text
<선택한 Orca CLI> orchestration ask --question "<최소 checkpoint 본문>" --environment local --json
```

## 판정

정식 승인 요청 준비 / 승인 검토 결과 / 질문 접수 / 조율자 수신 / 정확한 worker 종료를 각각 기록한다. 전송 성공으로 Auto-review 적용·공급자 실제 모델·전체 사용량까지 확인했다고 하지 않는다. 종료·취소는 기존 [관리 흐름](../runtime/routing-flow.md)을 사용하며 새 실행 한도를 만들거나 기존 한도를 초기화하지 않는다.
