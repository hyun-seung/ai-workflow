# 역할과 협업

이 문서의 책임·완료 기준은 실행 환경과 무관하다. 에이전트 생성·전달·상태·완료 수신은 [선택한 환경 가이드](../runtime/environments/README.md), 개발 규칙·테스트는 [프로젝트 지침](../projects/README.md)을 적용한다.

역할은 책임의 구분이다. 역할마다 항상 별도 에이전트를 실행하거나 모든 작업에 모든 역할을 참여시킬 필요는 없다. 한 에이전트가 여러 역할을 맡았다면 역할별 토큰이 독립적으로 측정됐다고 가정하지 않는다.

## 별도 학습 진입점

[학습 튜터](tutor.md) (`tutor`)는 개념 설명·학습 대화를 시작하는 별도 역할이다. 아래 개발 흐름의 하위 단계가 아니다. ELI5·80/20·제1원리·시각 정리와 요청 시 파인만 재설명을 선택하고, 이어서 궁금할 만한 연관 질문·답변을 공식 문서 우선의 근거 링크와 함께 제공한다. 독립적인 준비가 유익하면 [개념 해설](learning-concepts.md), [학습 시각화](learning-visuals.md), [연관 질문 해설](learning-connections.md) 담당으로 나누고 튜터가 통합한다. [진입·병렬 조건·순차 대화·사용 예시](../learning/README.md)를 참고한다.

## 작업 역할별 책임

| 역할 | 핵심 책임 | 결과물 |
| --- | --- | --- |
| [조율자](coordinator.md) | 목표·완료 기준, 작업 배정·의존성·예산, 결과 종합과 완료 판단 | 작업 계획, 결정·검증·사용량 보고 |
| [설계자](architect.md) | 기술 접근, 데이터·API·시스템 경계 설계와 설계 검토 | 기술 명세, 대안·선택 이유, 위험과 검증 항목 |
| [디자이너](designer.md) | 사용자 흐름, 화면·상태·시각 규칙, 접근성과 구현 화면 검토 | 화면·흐름 명세, 디자인 규칙, UI 검토 결과 |
| [백엔드 개발자](backend-developer.md) | 서버·데이터·API 구현과 자체 검증 | 코드, 테스트 결과, API 변경 사항 |
| [프론트엔드 개발자](frontend-developer.md) | 화면·상호작용·API 연동 구현과 자체 검증 | 코드, 테스트·브라우저 확인 결과 |
| [검증자](verifier.md) | 요구사항 충족, 검증 증거, 누락과 연동 문제의 독립 확인 | 통과·실패·미검증 항목, 재현 근거, 남은 위험 |

조율자는 검증자의 판정을 바탕으로 재작업과 완료를 결정한다. 검증자는 개발자의 테스트 책임을 대신하지 않으며, 개발자도 자신의 테스트만으로 모든 요구사항이 확인됐다고 단정하지 않는다.

## 실행 흐름

1. 조율자가 목표, 범위, 완료 기준과 허용 예산을 정리한다. 모호한 요구사항은 필요한 범위에서 확인한다.
2. 필요한 경우 설계자와 디자이너가 접근 방법과 화면·API 계약을 맞춘다. 작업 분리와 사용량 예측은 의존성·불확실성·검증 범위를 함께 고려한다.
3. 조율자가 독립적으로 검증할 수 있는 단위로 작업을 배정한다. 각 담당자에게 필요한 문서와 변경 범위만 전달한다.
4. 구현 담당자가 작업과 자체 검증을 수행한다. 서로 독립적인 범위에서만 병렬화하고, 같은 파일이나 계약을 동시에 바꾸면 조율한다.
5. 변경 영향에 맞게 검증자가 요구사항과 통합 결과를 확인한다. 실패 항목은 근거와 함께 해당 담당자에게 돌려보낸다.
6. 조율자가 결과, 중요한 결정, 검증 상태와 측정 가능한 사용량을 종합한다. 미검증 항목을 통과로 표시하지 않는다.

작은 수정은 기존 테스트와 간단한 확인으로 끝낼 수 있다. 별도 검증 세션은 여러 역할의 결과를 통합하거나, 인증·권한·데이터 손실·동시성·공개 게시 등 영향이 큰 작업에 우선 적용한다. 별도 세션도 오류가 없음을 보장하지 않으므로 실행 결과와 출처를 함께 확인한다.

## 개선 흐름

실행 완료 후 조율자가 재작업, 실패, 사용량 초과의 원인을 확인한다. 반복되는 문제에 한해 역할 지침·전달 정보·모델·effort 등의 변경을 제안하고, 검증자가 동일한 완료 기준의 대표 작업으로 개선 전후를 비교한다. 통과 기준을 낮춰 토큰을 줄이지 않는다.

개선 작업의 사용량도 별도로 포함한다. 처음부터 상설 최적화 에이전트를 만들지 않고, 검증된 변경만 공통 지침에 반영한다. 보안·성능·기술 조사 등의 전문 역할은 실제 필요가 생길 때 추가한다.

## 전달과 기록

- 작업을 넘길 때 목표·완료 기준, 관련 파일·계약, 담당 범위, 의존성, 허용 예산, 미해결 질문을 전달한다.
- 결과에는 변경 위치, 중요한 결정과 이유, 실제 검증 결과, 남은 문제와 사용량 측정 상태를 포함한다. 전체 대화나 내부 추론을 복사하지 않는다.
- [작업 입출력 양식](../templates/README.md)으로 배정과 결과를 연결할 수 있다. 동일한 작업 ID와 완료 기준 ID를 유지하며, [작업 보고 양식](../templates/task-report.md)은 전체 종합이 필요할 때 사용한다. 사소한 변경에 긴 보고서를 만들지 않는다.
- 실제 코드·로그·화면·경로를 포함하는 실행 기록은 기본적으로 비공개 자료로 취급한다. 보관 위치가 없으면 [개인정보 관리 기준](../principles/privacy.md)에 따라 저장 전에 확인한다.
