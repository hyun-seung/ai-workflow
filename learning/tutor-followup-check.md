# 후속 설명·시각화 보완 점검

2026-11-17 지침 보완과 작성 AI의 자체 확인이다. 실제 대화 원문·사용자 환경·실행 식별자는 기록하지 않는다. 아래 입력과 응답은 새로 만든 가상 예시이며 사용자 이해도·독립 평가·앱 자동 연결·비용 절감의 증거가 아니다.

## 발견한 경계와 수정

| 확인한 문제 | 수정 | 확인 수준 |
| --- | --- | --- |
| 후속을 이어 간다는 규칙은 있었지만 direct/reuse와 설명 방식 유지의 관계가 짧은 진입 지침에서 불명확 | 같은 목표의 꼬리 질문에도 튜터 기준 유지. 실행 선택과 설명 방식 구분 | 지침·작성 정책 입력 자체 확인 |
| 관계·흐름의 그림 선택이 상세 역할의 요청 신호에 치우치고 짧은 지침에 빠짐 | 관계·분기·권한 경계와 반복 혼란에 작은 도식을 먼저 선택. 약어·한 줄은 생략 | 새 가상 사례·표시 예시 자체 확인 |
| 텍스트 도식 대체가 지원 환경의 실제 표시 확인 없이 사용될 수 있음 | 지원하는 환경의 지침/스킬을 적용해 표시. 지원 불가·텍스트 대체·렌더 확인 수준 구분 | 예시 HTML의 화면 확인 범위만 아래에 기록 |
| 긴 표·본문·Q&A 반복이 이해를 돕는 표현 변경을 대신할 수 있음 | 새로 막힌 연결부터 답하고 예시·표현 변경. 같은 그림·Q&A 반복 생략 | 짧은 후속·한 줄 가상 사례 자체 확인 |
| 설계 고려사항에서 권한·네트워크 누락 가능 | 자원·권한·네트워크·장애·비용·운영 중 관련 축 확인. 주체별 권한 구분 | 설계 가상 사례의 기준 확인 |
| 지침을 읽었다는 사실을 전체 정상 동작으로 확대할 가능성 | 지침 참조·응답 기준 충족·앱 자동 연결 관측을 따로 보고 | 보고 가상 사례 자체 확인 |

새 시각화 기본값은 이번 개선으로 추가한 기준이다. 이전의 텍스트 대체 허용을 소급해 규칙 위반으로 단정하지 않는다. 기존에도 명시된 쉬운 설명·누락 방지·사용자 피드백 반영 기준은 별도로 적용한다.

## 가상 후속 사례

각 행의 선행 맥락은 해당 행에만 적용한다. 나열 순서를 하나의 대화로 가정하지 않는다.
이 표는 새로 작성한 응답·수용 기준의 자체 검토이며 실제 모델을 일곱 번 독립 실행한 결과가 아니다.

| ID | 입력과 필요한 맥락 | 보완 응답·수용 기준 |
| --- | --- | --- |
| TF-01 | 가상 파일 처리 시스템 입문: “요청, 작업 큐, 처리 워커가 어떻게 이어져?” | “큐는 처리할 일을 잠시 보관하고 워커가 꺼내 처리해요.” 뒤 요청→큐→워커의 작은 도식. 화살표는 작업 전달이며 권한·포함 관계로 표시하지 않음 |
| TF-02 | 앞에서 얕은 복사와 안쪽 객체 공유를 설명했음: “바깥과 안쪽 연결이 헷갈려.” | 같은 AI의 direct여도 참조 관계 도식을 제공. 서로 다른 바깥 리스트→같은 안쪽 객체를 표시하고 새 역할 승인·worker 없이 연결을 짚음 |
| TF-03 | TF-02와 같은 가상 주제를 별도 조건으로 사용. 기존 tutor 선택이 유효: “여전히 어려워. 안쪽 값을 추가하면?” | reuse를 유지하고 작은 변경 전후 예시로 표현 전환. `[[1]]`의 안쪽에 `2`를 추가하면 양쪽에서 `[[1, 2]]`를 본다는 공유 범위를 설명. 정의·이전 Q&A를 복제하지 않음. [공식 copy 정의](https://docs.python.org/3/library/copy.html#module-copy) |
| TF-04 | HTTP 캐시 설명 뒤: “HTTP 약어만 한 줄로.” | “HTTP는 Hypertext Transfer Protocol의 약자예요.” 기존 확인 근거를 사용하고 그림·Q&A를 강제로 추가하지 않음. [RFC 9110 §1](https://www.rfc-editor.org/rfc/rfc9110.html#section-1) |
| TF-05 | 가상 파일 처리 서비스: “워커들을 같은 서버에 배치할 기준은?” | 자원 요구·중단/장애·권한·네트워크·운영 정책을 검토해 관련 핵심만 설명. 앱의 버킷/큐 권한 차이만으로 서버 분리를 단정하지 않음 |
| TF-06 | 가상 EC2 기반 EKS의 권한 질문 | 하나의 노드 안에 두 Pod와 각 ServiceAccount→IAM Role 연결을 표시. Node Role과 앱 Role 구분, Pod Identity/IRSA와 IMDS 제한의 조건 포함. [AWS Pod Identity](https://docs.aws.amazon.com/eks/latest/userguide/pod-identities.html) |
| TF-07 | “튜터가 정상인가?” 또는 시각 도구 지원 불가 상황 | 지침 적용과 실제 응답/렌더 확인·앱 자동화를 구분. 도구가 막히면 텍스트 도식과 제한을 알리고 렌더 성공을 주장하지 않음. 새 도구·worker로 조용히 우회하지 않음 |

[확장·권한 도식 예시](tutor-followup-sample.html)는 TF-06과 구조·분기 설명의 표시 확인 자료다. EC2 기반 EKS에 대한 가상 설명이며 Pod 개수 제어와 노드 공급, 실행 위치와 권한 연결을 구분한다. 공식 문서를 재구성한 것이고 각 패널에 핵심 근거를 연결했다. HPA·KEDA의 관계는 Deployment/ScaledObject 범위이며 모든 KEDA 실행 방식으로 확대하지 않는다.

## 검증과 제한

- [작성 정책 입력](../examples/tutor-routing-cases.json)의 TR-18~21은 direct 후속·reuse 후속·약어 제한·설계 범위 점검이다. 정책 도구가 자연어 의미나 그림 품질을 자동 판정하는 것은 아니다.
- 설명·도식·근거 대응은 작성 AI의 자체 검토다. 실제 대화 원문을 저장하거나 사용자 발화를 공개 예제로 옮기지 않는다.
- 로컬 정책 결과와 실제 표시 확인은 수행 결과에 맞게 아래에 기록한다. 독립 재평가·다음 실사용의 만족도·반복 혼란 감소·비용 비교는 미검증이다.

확인 결과:

- 작성 정책 입력 21개의 기대 action과 비실행·추가 분류 모델 호출 없음 속성 확인. 신규 TR-18~21을 포함하며 자연어 분류 정확도 측정은 아니다.
- 관련 기존 회귀 검사 113개와 `workflow.py check --project .` 통과. 제품 코드·라우터 상태 계약·모델 설정은 변경하지 않았다.
- TF-03의 얕은 복사 예시를 Python으로 실행해 바깥 독립·안쪽 공유·변경 결과를 확인했다. HTTP 약어는 RFC 9110 §1, 참조 관계는 Python copy 문서, 그림의 KEDA·권한 관계는 공식 문서와 대조했다.
- 예시 HTML의 1000px·390px 로컬 프레임에서 고정/동적 확장·권한 패널 총 6상태의 실제 폭·가로 넘침 없음·선택 상태·표시 전환을 확인했다. 넓은 화면과 좁은 권한 패널의 스크린샷을 확인했다. 실제 앱 브라우저 폭이 viewport 요청과 달라 프레임 내부 폭을 직접 확인했으며 viewport 명령 성공만으로 크기 검증을 대신하지 않았다.
- 브라우저 표시 확인은 채팅 임베드의 사용자 측 표시 확인이나 전체 접근성 검사와 다르다. 도구 지원 불가 분기는 지침·가상 기준만 확인했으며 실제 장애 주입 시험을 하지 않았다.
- 기본 진입에는 추가 분류 모델·worker·이미지 생성 호출이나 매번 상세 문서 재주입을 추가하지 않았다. 지침 길이·도식 제작을 포함한 실제 전체 토큰 절감은 미측정이다.
