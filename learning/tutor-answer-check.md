# 질문 대상·근거 구분 점검

짧은 후속에서 질문 대상을 놓치거나 개념·메서드·관측값을 섞는 문제를 줄이기 위한 가상 사례다. 요청·응답·코드·HTML은 새로 작성했으며 실제 대화 원문·개인 환경·실행 기록을 포함하지 않는다. 작성 AI의 자체 검토이며 독립 모델 평가·실제 사용자 이해도·비용 절감 측정이 아니다.

## 응답 선택 기준

1. 현재 질문이 묻는 대상과 선행 조건을 고정한다. 횟수는 그 대상의 횟수, 추천은 선택과 이유부터 답한다. 관련된 다른 대상을 대신 답하지 않는다.
2. 개념적 동작, 실제 메서드 호출, 소스에서 도출한 값, 직접 관측한 값을 구분한다. 호출식 하나가 반복 실행될 수 있고 메서드 이름이 없더라도 기능이 다른 방식으로 구현될 수 있다.
3. 같은 질문이 재제기되면 직전 답의 대상 불일치를 먼저 확인한다. 같은 조건·예시의 막힌 단계를 추적하고 기존 그림의 그 부분을 갱신한다. 일반적인 추가 질문을 이해 실패로 단정하지 않는다.
4. 공식 페이지가 열리는 것과 해당 절로 이동하는 것을 구분한다. 확인한 절 ID만 사용하며, ID가 미확인이면 확인한 페이지와 절 제목으로 연결한다.
5. 조건·버전·주장이 같은 근거·그림·실험은 재사용한다. 새 주장·조건 변경·오류 의심에 필요한 부분만 추가 확인한다. 짧은 후속에는 기본 Q&A를 강제로 추가하지 않는다.

## 공통 가상 코드

동기적으로 차례로 실행하는 Python 예시다. 병렬 실행기나 실제 외부 API를 흉내 낸 성능 실험은 아니다.

```python
events = []

def render_one(value):
    events.append(("render_one", value))

def render_many(values):
    events.append(("render_many", None))
    for value in values:
        render_one(value)

render_many([4, 8, 12, 16])
```

## 가상 응답과 수용 기준

| ID | 질문·조건 | 응답 예시와 확인할 점 |
| --- | --- | --- |
| TA-01 | 공통 코드에서 “render_many는 몇 번 호출돼?” | “**1번입니다.** 그 안에서 원소 4개를 처리하는 render_one이 4번 호출됩니다.” 첫 답은 질문한 함수의 횟수. 원소 수 4를 render_many 횟수로 답하지 않음 |
| TA-02 | 공통 코드에서 “render_one 호출이 소스에 한 번 있으니 실제로도 한 번이야?” | “**실행은 4번입니다.** 호출식은 한 곳이지만 반복문이 원소마다 실행합니다.” 정적 호출식 개수와 동적 호출 횟수 구분 |
| TA-03 | TA-01을 다른 함수의 횟수로 잘못 답한 가상 조건에서 같은 질문 재제기 | “**render_many는 1번입니다. 앞선 답은 render_one의 횟수였습니다.** 같은 코드에서 바깥 호출 → 안쪽 반복 → 바깥 반환 순으로 보면 됩니다.” 질문 대상을 먼저 바로잡고 기존 그림에서 바깥/안쪽 호출 위치를 구별. 같은 장문·새 예시·전체 Q&A를 복제하지 않음 |
| TA-04 | 공통 코드에서 “전체 완료를 기다리는 건 join 호출이야?” | “**이 코드에는 join 메서드 호출이 없습니다.** 동기 함수가 안쪽 호출들을 마친 뒤 반환하는 흐름입니다.” 메서드 부재를 완료 흐름 부재로 확대하지 않음. 개념적 완료와 특정 API를 구분 |
| TA-05 | 함수 구현 없이 호출식 render_many(items)만 제공, 실행 기록도 없음 | “**제공한 코드에 바깥 호출식은 한 곳 있지만 내부 호출 횟수는 미확인입니다.** 내부 구현을 확인해야 합니다.” 추정치를 0이나 실측으로 바꾸지 않음. 실행을 관측하지 않았다면 정적 코드 범위만 설명 |
| TA-06 | 공통 코드와 기존 근거가 유효한 후속에서 입력 원소 수를 5개로 변경 | “**render_many는 여전히 1번이고 render_one은 5번입니다.** 바깥 호출은 그대로이고 반복 횟수만 바뀝니다.” 바뀐 조건만 반영. 기존 근거·그림을 재사용하고 불필요한 전체 재조사·별도 AI 호출을 추가하지 않음 |

이 표는 작성한 응답을 기준과 대조하는 자료다. 여섯 번의 실제 모델 실행·자동 채점 결과가 아니며 자연어 의미 판단을 코드가 보장하지 않는다. 같은 대화에 이어지는 행은 TA-03의 가상 조건처럼 명시한 경우뿐이다.

## 특정 절 링크의 가상 사례

아래 HTML은 공개 문서가 아닌, 이 점검을 위한 가상 원문이다.

```html
<h2 id="queue-limit">Queue limits</h2>
<a name="legacy-section"></a>
```

| 입력·확인 상태 | 올바른 처리 |
| --- | --- |
| 원문에서 queue-limit ID를 확인 | 해당 ID로 연결 가능 |
| 페이지는 열리지만 queue_limits ID는 없음 | 없는 ID를 사용하지 않음. 확인한 ID 또는 페이지·절 제목으로 대체 |
| 원문에서 legacy-section name을 확인 | 해당 앵커로 연결 가능 |
| 페이지 내용은 확인했지만 절 ID는 확인 불가 | 확인한 페이지 URL과 “Queue limits” 절 제목을 사용. ID 문자열을 추측하지 않음 |
| 기존 확인의 페이지·버전·절·주장이 같음 | 확인 결과 재사용. URL 변경·문서 갱신·오류 의심이 있으면 필요한 범위 재확인 |

HTML 앵커 존재 확인은 내용의 정확성 검증을 대신하지 않는다. 동적 페이지의 실제 이동·가독성·원격 페이지 상태까지 이 가상 HTML로 검증한 것은 아니다.

## 검증 범위

입력만 준비한 상태를 응답 품질 통과로 표시하지 않는다. 이번 자체 확인 결과는 다음과 같다.

- 문서의 공통 코드를 직접 실행해 render_many 1회·render_one 4회를 확인했다. 5원소 변형에서는 각각 1회·5회였다. 구분한 두 함수만 events에 기록했으며 Python 전체 내부 호출의 추적이 아니다.
- 같은 코드의 AST에서 render_many와 render_one 호출식이 각각 한 곳임을 확인해 정적 호출식과 동적 호출 횟수를 대조했다.
- 문서의 가상 HTML을 파싱해 queue-limit id·legacy-section name은 존재하고 queue_limits는 없음을 확인했다. 원격 문서 수집·자동 링크 수정기를 구현한 것은 아니다.
- TA-01~06의 작성 응답을 짧은 지침·상세/준비 역할·평가 양식과 자체 대조했다. 입력 대상·출처 수준·반복 혼란·재사용 기준이 일치한다. 실제 AI 응답의 자동 채점 결과가 아니다.
- 설정 검증과 기존 지침 전달 관련 회귀 54개를 통과했다. 라우터·앱 자동 연결·모델 설정·권한은 변경하지 않았다. 회귀 통과는 새 응답 기준의 자연어 판단 정확도·사용자 이해도 향상·토큰 절감을 뜻하지 않는다.

현재 상태: 지침·작성 사례의 자체 대조와 코드/가상 앵커·설정·기존 회귀 확인 완료. 수정본 독립 평가와 다음 실사용의 이해도·분량·비용은 미확인이다. 실제 사용자 대화와 실행 기록을 공개 저장소에 추가하지 않는다.
