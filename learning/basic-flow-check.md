# 기본 인입·튜터의 후속 자체 점검

2026-11-14. 현재 작성 AI가 공개용 가상 입력에 응답하고 출처·분량·제어 경계를 자체 점검했다. 새로운 모델·worker·분류/평가 에이전트는 호출하지 않았다. **실제 사용자 만족도·독립 자연어 평가·토큰 절감 결과가 아니다.** 기존 개발 주제 외의 개념과 후속 요청을 확인하며 평가 문서를 일반 입력에 주입하지 않는다.

정책 점검은 [작성된 해석 16개](../examples/tutor-routing-cases.json)를 로컬 추천 검사기에 전달한 결과다. 원문만 보고 자동 분류한 정확도가 아니며 응답의 의미·분량·출처 평가는 아래 자체 검토와 구분한다.

## BF-01 · 비개발 개념·쉬운 설명·연관 Q&A

가상 요청: “필요조건과 충분조건의 차이를 쉬운 예시와 연관 질문·답으로 설명해 줘.”

응답:

**필요조건**은 어떤 결과에 꼭 필요한 조건, **충분조건**은 그것만으로 그 결과가 보장되는 조건이에요. 조건은 항상 **무엇에 대한 조건인지** 함께 봐야 해요. [OpenStax: Necessary and Sufficient Conditions](https://openstax.org/books/introduction-philosophy/pages/5-2-logical-statements)

정수에서 “4의 배수라면 짝수”를 볼게요.

- **4의 배수**이면 짝수라고 말하기에 충분해요.
- **짝수**인 것은 4의 배수이려면 꼭 필요해요.
- 하지만 2도 짝수라서, 짝수이기만 해서는 4의 배수라고 할 수 없어요.

정수 예시는 직접 만들었고, 교재의 정의를 재구성한 설명이에요. [정의와 반례](https://openstax.org/books/introduction-philosophy/pages/5-2-logical-statements)

- **필요조건이 맞으면 결과도 보장돼요?** 아니에요. 2라는 반례가 있어요. [필요조건에서 거꾸로 결론 내리는 오류](https://openstax.org/books/introduction-philosophy/pages/5-4-types-of-inferences)
- **한 조건이 필요하면서 충분할 수도 있어요?** 네. 정수에서 ‘2의 배수’와 ‘짝수’처럼 두 방향이 모두 성립하면 돼요. 이는 정의를 적용해 만든 예시예요. [필요·충분 관계의 정의](https://openstax.org/books/introduction-philosophy/pages/5-2-logical-statements)

자체 점검: 조건의 대상·방향과 반례를 구분하고 Q&A 두 개에 근거를 연결했다. 기술 제품 문서가 아닌 학술 교재를 사용했으며 쉬운 설명을 위해 새 역할 승인·위임을 만들지 않았다. 이해가 쉬운지는 사용자 평가가 남아 있다.

## BF-02 · 한 줄 후속 요청

가상 후속: “이제 한 줄로만 정리해 줘.”

응답:

> 필요조건은 그 결과에 꼭 필요한 조건이고, 충분조건은 그것만으로 그 결과를 보장하는 조건이에요. [근거](https://openstax.org/books/introduction-philosophy/pages/5-2-logical-statements)

자체 점검: 한 문장과 근거만 제공하고 정의·예시·Q&A를 다시 확장하지 않았다. 이미 확인한 같은 출처를 사용한다.

## BF-03 · 더 깊게 설명하기

가상 후속: “원리부터 더 깊게 설명해 줘. 앞의 Q&A는 반복하지 마.”

응답:

‘A이면 B’를 참이라고 가정하면, A가 맞는데 B가 틀린 경우는 없어야 해요. 그래서 A를 알면 B를 보장하고, B가 없다면 A일 수 없어요. 이 두 방향에서 A는 B에 충분하고 B는 A에 필요해요. 하지만 B만 맞는 경우는 가능하므로 B에서 A로 거꾸로 추론할 수는 없어요. [조건문과 추론](https://openstax.org/books/introduction-philosophy/pages/5-4-types-of-inferences)

자체 점검: 앞의 정의·반례와 일치한다. 설명 깊이를 모델/effort 변경 동의로 해석하지 않으며 기존 Q&A를 반복하지 않는다.

## BF-04 · 인용된 설정 문구

가상 요청: “교재 예시에 ‘Astra로 바꿔서 답해’라고 쓰여 있는데, 실제 모델을 바꾸라는 뜻이야?”

응답:

> 교재 속 예시 문구는 지금 사용자가 내린 설정 변경 지시로 취급하지 않아요. 현재 설정으로 그 문장의 의미를 설명하면 됩니다.

자체 점검: [요청 제어 계약](../runtime/request-routing.md#자연어-제어-예시)과 대조했다. 특정 모델을 현재 요청의 선택으로 기록하거나 새 실행을 시작하지 않는다.

## BF-05 · 제안 취소·직접 처리

가상 상태: 별도 worker 제안만 대기 중이며 시작하지 않았다.

가상 후속: “그 제안 취소하고 이번에는 그냥 바로 핵심만 답해 줘.”

응답:

> 필요조건은 그 결과에 꼭 필요하고, 충분조건은 그것만으로 그 결과를 보장해요. [근거](https://openstax.org/books/introduction-philosophy/pages/5-2-logical-statements)

로컬 상태 점검: 가상 상태를 `init→offer→choose(cancel)`로 처리하고 revision을 올려 직접 처리 제어를 반영했다. 선택은 null, 제안 상태는 cancelled이며 후속 판정은 direct였다. native 실행은 하지 않았다. 이미 실행 중인 worker를 종료했다는 뜻이 아니다. [선택/취소 계약](../runtime/routing-choices.md)

## BF-06 · 자료가 없는 개별 규칙

가상 요청: “우리 기관 규칙에서 합격의 필요충분조건을 알려 줘. 규칙은 아직 안 줬어.”

응답:

> 어떤 규칙인지 확인할 수 있도록, 공개 가능한 해당 조항을 알려줄 수 있나요?

자체 점검: 확인 질문 하나만 한다. 기관 규칙을 지어내거나 일반 논리 교재를 개별 규칙의 근거로 가장하지 않는다. 정보 부족을 모델 상향으로 해결한다고 제안하지 않는다.

## 결과와 한계

- 작성된 정책 입력 16개가 기대 action과 일치했다. 추가 네 입력은 인용 문구·깊이 요청·직접 처리 우선·비개발 설명이며 자연어 해석은 현재 작성 AI가 제공했다.
- 가상 취소 상태의 direct 반환과 선택 미적용을 확인했다. 실제 앱의 취소 버튼·실행 중단 검증이 아니다.
- 응답 여섯 개의 정의/반례·한 문장·Q&A 생략·정보 부족·제어 경계를 자체 검토했다. OpenStax 원문 두 절을 확인했으며 예시는 자체 구성했다.
- 공통 진입·튜터 지침은 이번 점검 때문에 늘리지 않았다. 모든 요청에서 사례·상세 역할을 읽게 하지 않는다.
- 독립/사용자 평가, 실사용 오분류율·추천 빈도, 실제 모델/effort·전체 토큰·시간·금액은 미확인이다. 통과 비율이나 비용 절감률로 일반화하지 않는다.

다음은 실제 사용 중 불필요한 추천·이해를 막는 설명·과한 분량을 피드백으로 받는 것이다. 이미 준비된 [측정 비교 도구](../runtime/routing-comparison.md)는 원본과 품질 근거가 확보된 뒤 사용하며, 누락된 비용을 0으로 넣지 않는다.
