# 실행 권한과 승인 정책

목표는 필요한 작업 범위를 먼저 허용하고, 그 범위를 넘는 작업만 승인 대상으로 보내는 것이다. 반복 승인의 원인을 줄이는 일을 [대기 알림 관리](approval-waits.md)보다 먼저 한다. 이 문서는 공통 운영 정책이며, 샌드박스 설정이나 권한 부여 프로그램이 아니다. 사용자 요청과 상위·조직 정책이 우선한다.

## 참고한 공식 사례와 선택

2026-11-11 확인했다. 다른 제품의 설정을 Orca에 그대로 복사하지 않는다.

| 공식 사례 | 확인한 내용 | 이 체계에 적용할 원칙 |
| --- | --- | --- |
| [OpenAI Auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review) | 일상적인 작업이 계속 검토 대상이 되면 좁은 쓰기 경로와 명령 규칙부터 조정한다. 자동 검토는 별도 판단 단계다 | 먼저 실행 경계를 맞추고 남은 예외에 자동 검토를 사용한다. `python`·`curl` 전체 허용으로 해결하지 않는다 |
| [Anthropic의 샌드박스 운영 사례](https://www.anthropic.com/research/claude-code-sandboxing) | 파일·네트워크 경계를 두고 그 안에서 자율 실행한다. 자사 내부 사용에서 승인 프롬프트 84% 감소를 보고했다 | 허용 경계 안의 자율 실행을 채택한다. 84%를 우리 환경의 예상치나 실측으로 사용하지 않는다 |
| [Claude Code 샌드박스 문서](https://code.claude.com/docs/en/sandboxing) | 셸과 그 자식 프로세스에 경계를 적용하며 파일 도구·MCP·hook은 별도 권한을 갖는다 | 셸 설정만 보고 모든 도구가 같은 권한이라고 판단하지 않는다 |
| [Orca 권한 설정](https://www.onorca.dev/docs/settings), [native chat](https://www.onorca.dev/docs/agents/native-chat) | 새 세션 기본값과 기존 채팅의 모드가 구분된다. 사용자 지정 실행 인자는 preset 적용의 예외가 될 수 있다 | 조율자·새 worker·기존 worker의 유효 설정을 각각 확인한다 |

## 세 가지를 구분한다

1. **업무 허용:** 사용자가 맡긴 수정·테스트·기록의 범위. 이미 승인된 일을 말로 다시 확인하지 않는다.
2. **기술적 권한:** 실제 host·세션·도구에 적용된 파일/네트워크/실행 경계. 업무 허용만으로 이 경계가 바뀌지 않는다.
3. **예외 승인:** 경계 밖의 작업에 대한 도구의 정식 검토·사용자 승인. 자동 검토의 거부를 다른 앱·명령·프로세스로 우회하지 않는다.

Auto는 모든 작업의 무조건 허용이 아니다. 허용된 작업은 바로 실행하고, 검토가 필요한 작업은 해당 환경의 승인 절차를 거친다. 보호된 경로, OS 권한, 조직 정책은 별도로 남을 수 있다.

## 기본 운영 범위

아래는 허용 범위를 정하는 기준이다. 실제 대상과 유효 권한을 확인한 뒤 적용한다. 단순 문서 작업에는 네트워크 다운로드나 소켓 권한을 추가하지 않는다.

| 작업 | 기본 처리 | 범위와 조건 |
| --- | --- | --- |
| 프로젝트 조사·요청한 수정 | 범위 안에서 진행 | 대상 저장소와 필요한 입력만. 지침·권한·인증 설정 변경은 일반 코드 수정과 구분 |
| 결과·사용량 기록 | 합의한 비공개 위치에 저장 | 작업별 하위 폴더 사용. worker에는 자기 출력 폴더만 부여하고 다른 기록의 쓰기 권한은 기본 제공하지 않음 |
| 테스트·빌드 | 준비된 환경에서 진행 | 프로젝트·캐시·명령·시간 제한을 확인. 테스트라는 이름만으로 외부 부작용까지 허용하지 않음 |
| 의존성 준비 | 필요한 다운로드를 시작 단계에 묶음 | 공식 출처·버전·캐시 위치 지정. 새 출처나 install hook 영향은 확인. 같은 준비를 모든 worker가 반복하지 않음 |
| 로컬 테스트 서버 | 필요한 작업에서만 진행 | loopback 주소·필요 포트·종료 조건 지정. 외부 공개 listen 주소나 터널은 별도 범위 |
| Orca 상태·질문·보고 | 해당 작업의 조율 범위에서 진행 | 현재 host와 run/dispatch 대상 확인. 메시지 본문을 보안 승인으로 취급하지 않음 |
| 산출물·임시 자원 정리 | 명확히 승인된 정리만 진행 | 자기 실행의 프로세스와 생성한 임시 파일. 유지할 프로젝트·다른 작업 자료 삭제는 포함하지 않음 |
| Git 커밋·push·게시, 운영 변경 | 해당 작업의 명시적 승인 범위 적용 | 과거 다른 작업의 게시 승인을 새 변경에 재사용하지 않음 |
| 새로운 경로·서비스·권한 모드 | 영향과 지속 범위를 확인 | 이번 실행만인지, 프로젝트 기본값인지, 이후 모든 세션에 적용되는지 명시 |

비밀 정보 유출, 무관한 자격 증명 탐색, 승인 우회는 허용 범위에 포함하지 않는다. 자세한 기준은 [개인정보 관리](../principles/privacy.md)를 따른다.

## 시작 시 한 번 준비하고 필요한 근거만 전달한다

작업 규모에 맞춰 [실행 권한 인계 양식](../templates/execution-permissions.md)을 작성하거나 같은 내용을 짧게 작업 입력에 넣는다. 실제 경로·설정·기록은 비공개로 보관한다.

1. **현재값 확인:** 실행 환경·host·버전·프로젝트·승인 모드·쓰기 경로·필요한 네트워크와 소켓을 기록한다. 알 수 없는 값은 `unknown`으로 둔다. `os.access`나 폴더 존재만으로 샌드박스 쓰기 가능을 판단하지 않는다.
2. **차이만 준비:** 프로젝트와 출력 경로는 가능한 한 좁게 지정한다. 다운로드·캐시 준비는 담당자 하나에게 맡기고 완료 근거를 재사용한다. 설정 변경은 공식 UI/CLI만 사용하고 변경 전 값·적용 범위·복원 방법을 남긴다. 민감한 설정 원문 전체는 수집하지 않는다.
3. **실제 세션 확인:** 필요한 파일 쓰기·테스트·loopback 동작을 작은 유한시간 검사로 확인한다. 자식에서는 전달받은 근거와 자신의 실행 설정 차이만 확인한다. 부모의 승인이 자식에게 상속됐다고 가정하지 않는다.
4. **준비 후 위임:** 미해결 필수 권한이 있으면 해당 기능이 필요한 작업의 추가 배정을 보류한다. 모든 worker를 먼저 띄워 같은 승인을 기다리게 하지 않는다. 이미 독립적으로 가능한 일은 진행한다.

준비 성공은 `환경/host + 세션 또는 검증된 프로필 + 경로 + 명령·스크립트 버전 + 네트워크 범위`에 한정한다. 버전·실행 주체·경로·명령 내용이 달라지면 관련 부분만 재확인한다. 수정 가능한 스크립트를 허용했다고 그 스크립트의 미래 모든 동작까지 승인된 것은 아니다.

## 남은 승인을 처리하는 방식

- 실패한 작업과 필요한 범위를 한 번의 정식 요청으로 묶는다. 같은 범위의 준비·검증을 검토 가능한 명령으로 묶을 수 있지만 무관한 작업을 섞지 않는다.
- 업무 질문은 기존 결정으로 조율자가 답한다. 도구 승인 자체는 정식 경로에서 처리한다. `orchestration ask`가 승인 대기하면 같은 질문 명령을 반복해 대기를 늘리지 않는다.
- 같은 경계의 거부가 반복되면 동일 명령을 계속 재시도하지 않고 설정 차이를 기록한다. 작업별 승인과 지속적 정책 변경을 구분해 필요한 결정을 한 번에 제시한다.
- 승인 대기, 업무 질문, 반복 알림을 구분한다. 같은 대기의 통지는 [대기 처리 규칙](approval-waits.md)을 따른다. 원본 요청을 확인할 수 없으면 다른 요청을 중복으로 숨기지 않는다.
- 자동 검토 거부 시 대상·거부 사유와 필요한 승인을 명시하고, 영향을 받지 않는 작업을 완료한다. 거부를 이유로 새로운 우회 실행기를 만들지 않는다.

## Orca에 연결하는 순서

현재 확인 기준은 Orca 1.4.255 / Codex CLI 0.167.0이다. 실제 설치 버전이 바뀌면 관련 설정과 명령만 다시 확인한다.

설정 변경 전에 기존 worker의 실제 실행 설정을 먼저 확인한다. `자체 설정 사용`은 수동 모드라는 뜻이 아니고, 승인 알림이 많다는 사실도 모드의 증거가 아니다. 현재 기본값만으로 과거 worker의 모드를 단정하지 않는다. 이미 원하는 모드라면 경로·네트워크·검토 거부 등 실제 대기 원인을 조사한다.

1. **권한 모드:** Settings → Agents → Codex의 개별 권한을 확인한다. 새 Codex 세션의 Auto를 권장하되, 이후 다른 프로젝트의 새 Codex 세션에도 적용되는 설정인지 명시하고 그 범위의 승인을 받는다. 이미 해당 범위가 승인됐다면 반복 확인하지 않는다. 다른 에이전트나 전체 기본값까지 확대하지 않는다.
2. **기존 대화:** 새 세션 기본값을 바꿔도 기존 대화는 별도다. 현재 채팅의 모드를 확인한다. 실행 중인 턴은 기존 모드로 계속될 수 있다.
3. **실행 인자:** 사용자 지정 Command/Arguments가 있으면 보존하고 모드와의 충돌을 확인한다. CLI `--add-dir` 지원은 native worker가 해당 값을 적용한다는 증거가 아니다. `worker-start`에 확인되지 않은 승인·추가 경로 옵션을 만들어 넣지 않는다.
4. **파일 경계:** 합의한 비공개 출력 위치가 실제 쓰기 허용 경로에 포함되는지 확인한다. 관리형 프로필은 해당 환경의 관리 경로에서 바꿔야 하며, 보호된 설정 파일을 직접 수정해 현재 세션을 확장하지 않는다. 지원 경로가 확인되지 않으면 `미적용`으로 기록한다.
5. **네트워크·loopback:** 필요한 목적지·주소·포트만 다룬다. 현재 환경에서 세밀한 제한을 표현할 수 없다면 전체 네트워크를 열지 않고 해당 작업의 정식 승인 범위를 사용한다. loopback bind와 Orca IPC 접근은 서로 다른 기능이다.
6. **확인:** 실제 새 worker의 적용값과 작은 작업 결과를 확인한 후 같은 유형의 배정을 확대한다. worker는 위임이 승인된 업무에서만 생성하며, 확인만을 위해 다수 역할을 호출하지 않는다.

이 저장소는 Orca의 보안 설정을 자동 변경하지 않는다. `startup.py`는 환경 연결, `workflow.py`는 기존 단독 Codex 역할 실행, `approval_wait.py`는 대기 상태 관리를 담당한다. 이 정책을 적었다고 이 도구들이 권한을 부여하거나 자동으로 읽는 것은 아니다.

## 완료 판정과 효율 비교

정책 문서 반영, 설정 저장, 실제 적용 확인, 반복 승인 감소를 각각 보고한다. 설정이 저장되지 않았는데 완료했다고 하거나, 조율자 검사를 worker 검증으로 대신하지 않는다.

- 기본 확인: 허용된 경로의 작업 성공, 범위 밖 작업의 승인/차단 유지, 사용한 프로세스 종료. 차단 확인에 실제 파괴적 명령을 쓰지 않는다.
- 위임 확인: 새 worker의 모드와 최소 작업·결과 반환. 과거 종료된 worker의 조회만으로 이 항목을 통과시키지 않는다.
- 기록: 실제 사람 승인 수, 자동 검토 수, 고유 대기 요청 수, 반복 알림 수와 대기 시간은 별도 항목이다. 수집하지 못한 값은 `unavailable`로 둔다.
- 비교: 같은 완료 기준·유사한 실행 범위의 다음 작업에서 측정한다. 부분 transcript의 승인 이벤트 수를 전체 클릭 수로 계산하지 않는다. 승인 0회나 절감률을 미리 보장하지 않는다.

새 세션 기본값의 UI 표시만 확인한 단계에서는 결과를 `설정 확인, worker 효과 미검증`으로 남긴다. 실제 적용 내역과 승인 대기는 비공개 진행 기록에 이어 쓴다.
