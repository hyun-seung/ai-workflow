# 제한된 병렬 위임 — 검토안

상태: 2026-11-10 설계 검토. 아래 값과 설정 키는 제안이며 현재 실행기가 읽거나 강제하지 않는다. 모델·effort 설정과 별도로 공통 위임 정책을 정하고, 실행은 환경 네이티브 기능을 사용한다. 기존 단독 Codex 프로토타입의 고정 순차 흐름을 공통 기본값으로 삼지 않는다.

## 선택 기준

작은 작업은 한 담당자가 처리한다. 규모가 커졌을 때는 의존성·파일 소유·공유 자원부터 확인해 독립적인 작업을 병렬로 배정한다. 한 담당자가 충분하다는 판단은 병렬화 가능한 부분을 검토한 뒤 내린다. 상한은 동시에 채워야 하는 목표 인원이 아니다.

역할마다 worker를 하나씩 만들거나 동일 업무 전체를 여러 모델에 중복 배정하는 것은 기본 동작으로 삼지 않는다. 준비된 작업 중 후속 작업을 가장 오래 막는 작업부터 시작한다. 병렬화로 줄어드는 대기보다 인계·공유 파일 충돌·통합 비용이 클 것으로 판단되면 묶어서 맡긴다. 정확한 시간 추정이 없으면 가설로 기록한다.

### 같은 변경은 한 담당자에게 묶기

배정 단위는 직함보다 완결된 변경이다. 같은 파일·설정을 함께 바꿔야 하거나 앞선 변경의 판단 맥락을 계속 사용해야 하면 한 담당자에게 묶어 순차 처리한다. 동시에 수정할 수 없는데 담당자만 둘로 늘려 대기·인계를 만드는 것은 기본 배정 방식으로 삼지 않는다. 같은 파일을 독립 검증자가 읽는 것은 수정 담당을 나누는 것과 구분한다.

공통 설정 하나가 여러 작업에 걸친다면 그 설정을 지정 담당자가 먼저 확정하고, 준비된 계약을 사용하는 독립 작업을 이후 병렬로 배정할 수 있다. 공통 파일이 있다는 이유로 요청 전체를 끝까지 순차 처리하지 않는다. 파일이 달라도 API·스키마·공유 포트·DB 상태 등 의존성이 있으면 계약이나 자원 격리가 먼저 필요하다.

| 관계 | 기본 배정 |
| --- | --- |
| 같은 파일·설정을 함께 수정 | 한 담당자의 연속 작업으로 묶음 |
| 공통 설정 뒤 수정 범위가 분리됨 | 공통 단계 완료 후 독립 작업 병렬 배정 |
| 수정 파일은 다르지만 결과 의존성이 있음 | 필요한 선행 결과를 확정한 뒤 배정 |
| 안정된 공통 자료를 읽고 독립적으로 수정 | 같은 필요한 참조를 전달하고 병렬 배정 |

실행 중 공통 파일 변경이 새로 필요해지면 해당 변경을 소유 담당자에게 모은다. 충돌하는 쓰기를 진행한 뒤 병합에 맡기지 않는다. 영향을 받지 않는 다른 작업은 계속할 수 있다. 이는 현재 배정 규칙이며 파일 쓰기를 실행 환경에서 강제 차단하는 기능은 아직 없다.

### 조율자가 공통 맥락을 선별해 전달하기

조율자는 이번 요청에 공통으로 필요한 요구사항·제약·인터페이스부터 확인하고, 역할별로 필요한 부분과 참조를 짚어 준다. 프로젝트 전체를 미리 정독하거나 모든 구현 결정을 대신하지 않는다. 각 구현의 세부 조사는 해당 담당자가 맡는다.

인계 내용은 기존 `task-input`의 필드로 간결하게 작성한다.

- 목표·완료 기준과 담당 수정 범위.
- 이미 확정한 공통 계약, 반드시 지켜야 할 조건과 예외.
- 필요한 원문 구간과 파일/문서 위치, 그 부분을 참고해야 하는 이유.
- 확인한 버전·해시·관련 미커밋 변경, 사실과 추정·미확인 구분.
- 선행 결과·다른 담당자와의 경계, 범위를 바꿔야 할 때 전달할 대상.

짧고 정확한 원문은 필요한 부분을 발췌하고, 길거나 반복되는 배경은 요약한다. 원문 접근은 유지하며 수신자가 결론·불일치·오류를 확인할 때 관련 범위를 추가로 읽을 수 있어야 한다. 조율자 요약으로 환경이 요구하는 필수 지침이나 독립 검증자의 원래 요구사항·실제 증거 확인을 대체하지 않는다. 원본이 바뀌면 영향을 받는 담당자에게 변경된 계약과 버전을 알린다.

목표는 공통 자료의 반복 탐색과 불필요한 전체 읽기를 줄이는 것이다. 각 worker는 전달된 자료를 자기 문맥에서 읽으므로 조율자가 한 번 읽었다고 읽기 비용이 0이 되지는 않는다. 조율자의 조사·요약과 추가 인계 비용까지 포함해 비교한다.

기존 [작업 입력 양식](../templates/task-input.md)의 `context`와 [자료 전달 규칙](../templates/README.md)을 재사용한다. 단독 Codex 경로에는 명시 파일 구간을 전달하는 `workflow.py --context-file`이 있고, [인계 준비 도구](harness.md)는 명시 파일의 경로·해시를 확인한다. 현재 두 도구 모두 역할별 관련 내용을 자동 선별하지 않으며 native worker의 공유 문맥을 만드는 기능도 아니다.

## 서로 다른 세 가지 동시성

| 대상 | 예 | 통제 위치 |
| --- | --- | --- |
| 역할 작업 | 서버 구현과 클라이언트 구현 | 공통 위임 정책 + 환경 연결 |
| 테스트 케이스 실행 | 서로 독립된 Net/NIO 케이스 | 프로젝트 테스트 실행기 |
| 한 케이스의 요청 | 풀 크기 3에 동시 요청 6회 | 테스트 명세의 입력 조건 |

에이전트를 늘리지 않고도 테스트 실행기는 케이스를 병렬 실행할 수 있다. 반대로 케이스 안의 요청 수를 줄이면 원래 시험 조건이 바뀐다. 세 값을 하나의 병렬 수로 합치지 않는다.

## 권장 초기 한도

자동 강제 기능이 생기기 전에는 조율자가 [작업 입력](../templates/task-input.md)에 조율자 전체의 동시 상한, 해당 요청의 누적 배정 상한과 현재 사용 수를 기록한다. 여러 작업을 위임할 때 실행 환경이 허용하는 범위에서 작업 크기에 맞는 값을 정하고 사용자 지정값이 있으면 우선한다. 아래 숫자를 묵시적으로 확정값으로 쓰지 않는다. 한도 안에서 준비된 독립 작업이 하나뿐이라면 하나만 시작한다.

| 정책 | 예시값·방식(미확정) | 의미 |
| --- | --- | --- |
| `max_active_workers` | 2 | 조율자 외 하위 worker. 같은 조율자가 관리하는 모든 요청·Run의 합계 |
| `max_dispatches_per_request` | 6 | 한 사용자 요청에서 새 작업 배정·후속 재배정·재시도의 누적 한도 |
| 중첩 위임 | 조율자에게 재배정 요청 | 하위 worker가 별도 worker를 만들어 상한을 우회하지 않음 |
| 테스트의 `max_parallel_cases` | 처음에는 1 | 프로젝트에서 자원 격리·결과 동등성을 검증한 뒤 2부터 별도로 검토 |

2명과 6회는 검토용 예시이며 사용자 확정값이나 측정으로 얻은 최적값이 아니다. 2명을 고정 상한으로 삼지 않는다. 요청에 맞춰 최대 인원을 설정하고, 실제 배정은 준비된 독립 작업 수와 남은 동시·누적 한도 안에서 한다. 3개 이상의 독립 작업과 충분한 한도가 있으면 그에 맞춰 배정할 수 있다. 실행 도중 한도에 닿으면 현재 결과·남은 필수 검증을 보고하고 범위를 재계획한다. 필수 검증을 생략하거나 새 request ID를 만들어 누적 한도를 초기화하지 않는다.

공통 기본값 → 프로젝트 정책 → 요청의 명시 설정 순서로 유효값을 확정하고 기록하는 구성을 제안한다. 외부 런타임이 더 낮은 한도를 두면 그 한도를 따른다. 지원하지 않는 설정은 오류로 알리며 무시하지 않는다. 현재 `workflow.json`은 단독 Codex 역할 설정이므로 여기에 미지원 키를 넣지 않는다. 파일명·CLI는 연결 구현 때 확정한다.

### 슬롯과 누적 횟수

- 시작 예약·실행 중·승인/질문 대기·종료 처리·실행 여부 불명은 활성 슬롯을 차지한다. 승인 대기 worker를 제외하고 새 worker를 계속 늘리지 않는다.
- 같은 슬롯의 worker를 재사용할 수 있지만 새 후속 작업은 누적 배정 횟수에 포함한다. 동일 요청 ID의 접수 여부를 확인하거나 같은 접수 결과를 조회하는 것은 중복 계산하지 않는다.
- 진행 중 작업에 대한 단순 정보 보완·질문 답변은 새 배정이 아니다. 이 횟수 제한만으로 모델 턴·토큰·실행 시간이 제한되지는 않는다.
- 완료 알림만으로 프로세스 종료를 가정하지 않는다. 네이티브 상태에서 종료·회수 또는 기존 슬롯의 안전한 재사용을 확인한다. 남겨 둔 worker와 실행 여부 불명 상태도 별도로 기록한다.
- 대기 작업은 에이전트를 미리 띄워 두지 않는다. 선행 결과가 준비되고 슬롯이 있을 때 생성한다. 완료·해소 알림으로 다음 배정을 판단하며 반복 조회 루프를 만들지 않는다.
- 다른 조율자의 실행까지 포함하는 기기 전체 한도는 별도 범위다. 위 정책을 OS 전체 제한으로 설명하지 않는다.

## TCP 유형 업무의 배정 예

1. 조율자가 메시지 경계·요청/응답 필드·제어 명령·로그·산출물 경로와 완료 기준을 짧게 확정한다.
2. worker A는 독립 서버·장애 제어·서버 로그를, worker B는 클라이언트·팩토리 구성·케이스 실행기를 병렬로 구현한다. 공유 파일은 담당자 한 명만 수정한다.
3. 인터페이스가 준비되면 smoke test와 통합 실행을 한다. 서버 작업이 완료돼 빈 슬롯이 생기면 독립 검증자가 요구사항·원시 로그 검사 준비를 시작할 수 있다. 최종 판정은 확정된 산출물·실제 실행 결과 뒤에 한다.
4. 실행 담당자가 원시 결과와 케이스 집계를 반환하고 검증자가 대조한다. 조율자가 사용자에게 결과를 전달한다. 보고서만 쓰는 별도 worker는 기본적으로 추가하지 않는다.

한 worker가 서버와 클라이언트 전체를 구현한 뒤 검증하는 순차 방식도 작은 범위에서는 타당하다. 선택 이유와 병렬화할 수 있었으나 묶은 부분을 짧게 기록해 다음 실적 비교에 사용한다.

테스트 병렬 실행에는 충돌 없는 포트 할당·유일한 run/케이스 출력 경로·프로세스 소유권·종료 보장·CPU 부하에 따른 timeout 영향 확인이 먼저 필요하다. 빈 포트를 검사한 뒤 소켓을 닫고 나중에 서버를 시작하는 방식은 병렬 예약이 아니다. 초 단위 시각만으로 run 폴더를 정하면 동시에 시작할 때 충돌할 수 있다. 공유 머신에서 기능 시험의 실패 조건이 달라지지 않는지 검증한다.

## 환경 연결의 최소 구현 범위

설치된 Orca의 `coordinator-loop` 가이드는 task 의존성·ready 목록·worker 시작을 제공한다. `run-create` 도움말에서 Run 자체는 스케줄러가 아니며, 확인한 `worker-start`·`run-create`에는 동시 worker 상한 옵션이 없다. `worker-list --limit`는 목록의 페이지 크기다. 이것을 실행 한도로 사용하지 않는다. [공식 CLI 안내](https://www.onorca.dev/docs/cli/overview)와 해당 설치 버전의 `skills get orchestration`·하위 명령 help를 기준으로 연결한다.

공통 계층에는 정책 읽기·준비된 작업의 배정 허용 판단만 둔다. Orca 연결에서는 `worker-start`와 완료 worker에 대한 `send` 등 새 실행을 만드는 모든 관리 경로를 같은 검사로 통과시키고 실제 생성·인계·상태·결과는 Orca를 사용한다. Paseo는 이후 같은 계약을 지원 기능에 맞춰 연결한다.

엄격한 한도를 구현하려면 검사와 슬롯 예약이 원자적이어야 한다. 동시 실행 요청 두 개가 같은 빈 슬롯을 보지 않도록 공유된 비공개 상태에 예약을 먼저 남긴다. native 요청 식별자·접수 결과와 연결하고, 프로세스 중단이나 응답 유실 뒤에는 원래 접수·실행을 확인한 후 재개한다. 실행 여부가 불명확하면 예약을 지우거나 새 실행을 만들지 않는다. native mail을 소비하는 별도 poller는 만들지 않는다.

상태 목록은 명시적인 Run 범위·페이지 끝까지 확인하며 같은 물리 worker를 중복 계산하지 않는다. 단순 지침이나 시작 출력에 숫자를 적는 것만으로는 강제 상한이 아니다. 이 연결을 거치지 않는 직접 CLI·다른 세션의 실행까지 차단할 수 있다고 주장하지 않는다.

## 완료 기준과 효과 확인

다음 구현은 위 배정·맥락 전달 기준과 정책 설정·생성 전 제한·네이티브 연결 하나로 범위를 좁힌다. 가짜 환경 응답으로 한도 1/2/3, 같은 파일 수정의 단일 담당 처리, 선행 계약 이후 병렬 배정, 대기·불명 상태, 동시 예약, 재시도·후속 작업, 재시작 후 복구를 먼저 검사한다. 실제 Orca에서는 두 개의 작은 독립 작업과 세 번째 대기로 상한·빈 슬롯 재사용·결과 수신을 확인한다. 위임이 끝난 뒤 프로세스를 정리한다.

효율 비교는 같은 완료 기준에서 요청 접수→최종 결과 전달 시간, 구현·명령 실행·승인 대기·통합·검증·재작업 시간을 분리한다. 병렬 시간은 단순 합산하지 않고 전체 경과 시간도 함께 본다. 배정 수·승인 요청·재작업·실패를 기록하고, 토큰은 측정값이 있을 때만 비교한다. 현재 기록만으로 병렬화의 절감률을 확정하지 않는다.
