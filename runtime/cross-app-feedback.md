# 다른 앱 적용과 여러 PC의 결과 수집

공통 지침을 다른 앱에서 사용하는 것과 실행 데이터를 자동 수집하는 것은 별개다. 이 문서는 현재 가능한 연결과 앞으로 구현할 수집 구조를 구분한다. 중앙 서버·저장소·다른 앱 설정을 생성하거나 활성화하지 않는다.

## 현재 지원 범위

| 항목 | 현재 상태 |
| --- | --- |
| 공통 원칙·역할·완료 기준 재사용 | 대상 프로젝트에 실제 접근 가능한 지침을 명시적으로 연결 |
| Orca 로컬 Codex의 등록 배정 Stop 수집 | 프로젝트별 설치·정확한 정의 신뢰와 실제 수입을 확인한 범위에서 지원 |
| 일반 결과 JSON/JSONL의 SQLite 수입·조회 | 기존 교환 형식의 명시 수입·내보내기 지원 |
| Paseo의 실행 결과 자동 변환 | 미구현·실제 실행 수집 미검증 |
| Codex 앱의 실행 결과 자동 변환 | 미구현·실제 실행 수집 미검증 |
| 여러 PC의 업로드·재전송·중앙 통합 | 설계 대상, 현재 자동 연결 없음 |

기존 Orca 수집기는 Orca task/dispatch와 명시 ledger를 검사한다. 같은 Codex 공급자를 사용하더라도 Paseo나 Codex 앱의 세션을 Orca 배정으로 가장해 수입하지 않는다. 질문 후 같은 배정을 이어가는 등 현재 파서가 구간을 확정하지 못하는 실행은 부분 측정 또는 미측정으로 남긴다.

## 앱별로 지침을 적용하는 순서

1. 공통 저장소의 사용할 커밋과 대상 프로젝트를 정한다. 각 PC에서 읽을 수 있는 로컬 경로를 확인한다.
2. [프로젝트 연결](../projects/README.md)에 따라 공통 `AGENTS.md`, 필요한 역할 문서·로컬 역할 스킬, 대상 프로젝트의 지침과 테스트 명령을 연결한다. 이 저장소의 역할 문서를 앱의 native agent 등록으로 간주하지 않는다.
3. 앱·공급자·실행 host·작업 공간을 구분한다. 앱 설치 여부로 현재 환경을 선택하지 않는다.
4. 해당 앱에서 작은 작업의 지침 로드·파일 접근·검증 결과를 확인한다. 그 뒤에 결과 수집을 별도로 검증한다.

Paseo는 [환경 가이드](environments/paseo.md)에 따라 실제 daemon host와 agent/workspace를 대조한다. 공식 [provider 설명](https://paseo.sh/docs/providers.md)은 Paseo가 설치된 agent CLI를 실행하는 구조임을 설명한다. 앱과 공급자 이름을 서로 바꾸어 기록하지 않는다. [CLI의 usage](https://paseo.sh/docs/cli.md)는 계정 quota·잔액 조회이며 개별 작업 토큰으로 합산하지 않는다.

Codex 앱에서는 프로젝트 지침과 필요한 로컬 파일 접근을 확인한다. 현재 `startup.py`의 환경 선택은 Orca/Paseo를 위한 것이므로 Codex 앱에 `--environment codex`라는 미지원 값을 만들지 않는다. Codex 앱에서는 공통 지침을 명시적으로 연결하고, native 위임·완료·측정 기능은 그 앱의 지원 기능으로 따로 확인한다. 로컬 hook 지원과 cloud orchestration 지원은 다르다. [공식 hooks 문서](https://learn.chatgpt.com/docs/hooks)의 적용 환경·정확한 정의 신뢰 절차를 확인하며, 대화에서 “승인”이라고 답한 것을 hook 신뢰 설정으로 처리하지 않는다.

## 지금 사용할 수 있는 수동 교환

다음은 가상 경로다. `result.jsonl`은 이미 공통 형식으로 검증·등록한 한 요청의 기록이며, Paseo 로그나 Codex 원본을 직접 변환하는 명령이 아니다.

```sh
python3 scripts/trace_viewer.py --db /private/example/local.sqlite3 \
  export --request-id request_example --format jsonl > /private/example/result.jsonl
python3 scripts/trace_viewer.py --db /private/example/combined.sqlite3 \
  import /private/example/result.jsonl
```

두 번째 명령은 파일을 이미 받은 PC에서 실행한다. 네트워크 전송·업로드는 수행하지 않는다. [수입 계약](trace-viewer.md)과 [사용량 검증](trace-usage.md)을 유지하며, 같은 파일의 재수입과 상충 자료의 거부를 확인한다. 파일과 DB는 승인된 비공개 위치에 보관한다. 새 출력 파일을 만들기 전에 소유자 전용 디렉터리·파일 권한과 기존 출력 충돌을 확인한다.

**기존 export는 원문 이벤트·개인 경로를 포함할 수 있다.** 현재 명령에 개인정보 제거·최소화 기능이 있다고 가정하지 않는다. 검토하지 않은 bundle을 자동 업로드하지 않는다. 분석용 최소 자료를 만드는 별도 변환 규약이 필요하며, 기존 원본·검증 근거를 덮어쓰거나 해시를 조작하지 않는다.

## 여러 PC의 수집 구조

목표 흐름은 `각 PC의 로컬 기록 → 전송할 결과 묶음 → 중앙 수신함 → 검증·중복 확인 → 통합 조회`다. SQLite는 각 PC의 로컬 기록용으로 계속 사용할 수 있다. 중앙 저장 방식은 전송 구조와 별도로 선택한다.

- 실행 중인 SQLite 파일을 동기화 폴더에 놓고 여러 PC가 함께 쓰는 방식으로 연결하지 않는다. 완료한 결과 묶음을 전달한다.
- 중앙 보관 위치, 운영 host, 접근 주체, 전송 주기와 보관 기간을 먼저 정한다. 파일 업로드 방식과 API 수신 방식 중 초기 범위를 선택한다. 특정 서비스·중앙 DB 종류는 아직 확정하지 않았다.
- 묶음 ID·내용 해시·스키마 버전·생성 시각·출처를 보존하고 수신 확인 후 전송 완료로 기록한다. 끊긴 전송은 같은 묶음으로 재시도한다. 이 전송·수신 확인 기능은 미구현이다.
- 동일한 provider session/turn이 다른 앱·PC를 거쳐 다시 들어와도 같은 물리 구간을 중복 합산하지 않는다. 충돌 자료는 보류하고 출처를 확인한다. 앱 이름을 붙여 새 측정처럼 복제하지 않는다.
- 일반 결과와 native 측정의 검증 수준을 구분한다. 토큰이 없으면 미측정이며 실행 시간·비용·계정 잔액으로 추정하지 않는다.

최소 수집 후보는 workflow 커밋·스키마 버전, 앱/provider/host의 구분, 요청·역할·작업·재시도 계보, 실제 확인 모델·effort, 측정 출처·구간·완전성, 검증 판정과 재작업 사유다. 시간·승인 대기는 실제 관측된 경우에만 포함한다. 인증정보·대화 원문·사용자 코드·도구 입력 원문은 기본 전송 대상에서 제외한다. 필요한 상세 자료의 공유 범위는 별도로 확인한다.

## 구현과 수용 순서

1. 사용할 앱과 실행 host별 지침 적용 방법을 검증한다.
2. 중앙 보관 위치·전송 방법·최소 데이터·접근 범위를 결정한다.
3. 앱별 결과 변환과 최소 자료 묶음의 형식·출처 검증을 구현한다.
4. 업로드·수신 확인·실패 재시도·중복 및 충돌 처리를 구현한다.
5. 두 PC에서 같은 묶음 재전송, 연결 단절 후 재개, 다른 앱에서 같은 구간 재수입을 검증한다. 누락을 숨기지 않는다.
6. 통합 대시보드에서 앱·역할·workflow 버전별 품질·토큰·시간·재작업을 비교한다. 동일한 완료 기준으로 개선안을 검토한 뒤 지침에 반영한다.

실행 기록이 쌓였다고 규칙·모델·권한을 자동 변경하지 않는다. [작업 보고](../templates/task-report.md)와 [공개·비공개 기준](../principles/privacy.md)에 따라 실제 자료는 비공개로 유지하고, 공개 저장소에는 범용 개선과 가상 예시만 반영한다.
