# 요청 시간과 토큰 단가 추정 비교

상태: 비교 manifest v2에 선택적인 시간 기록과 단가표를 연결했다. 계산은 읽기 전용이며 모델·worker·네트워크·요금 조회를 실행하지 않는다. 현재 공개한 실제 요금·시간/금액 절감 결과는 없다. [기존 v1](routing-comparison.md)은 그대로 지원하고 두 지표를 null로 반환한다.

## 입력과 결과

[v2 비교 양식](../templates/routing-comparison-v2.json)은 v1의 완료 기준·측정 파일·수집 범위·품질을 유지하면서 다음을 선택적으로 추가한다.

- 각 방식의 `timing`: [요청 시간 기록](../templates/routing-timing.json)의 `{path, sha256}` 참조.
- 최상위 `rate_card`: 두 방식에 사용할 [단가표](../templates/routing-rate-card.json)의 `{path, sha256}` 참조.

필요 없는 항목은 생략한다. null 날짜·단가·0으로 채운 해시는 미작성 자리표시자이며 유효한 측정 입력이 아니다. 실제 파일·stdout은 기존과 같이 Git/대상 프로젝트 밖의 비공개 폴더 0700·파일 0600에 둔다. 중첩된 근거 참조도 명시 파일만 읽고 해시·크기·형식을 검사한다. 원본 metadata 안의 다른 경로·URL을 따라가거나 가격을 자동 검색하지 않는다.

```sh
python3 scripts/compare_routing.py --project /private/example/project --manifest /private/example/comparison-v2.json
```

두 결과의 `decision`은 여전히 토큰·선언된 품질/수집 범위에 따른 기존 판정이다. v2는 `decision_basis: tokens_with_quality_and_coverage`를 명시한다. 토큰이 적어도 더 비싸거나 오래 걸릴 수 있으므로 시간·단가 추정 결과를 별도로 읽는다. 모든 결과의 `automation_allowed`는 false다.

## 요청 전체의 경과 시간

시간 기록에는 해당 `request_id`, 고유 `measurement_id`, 시계 출처를 구분하는 `clock_id`, 시작/종료 시각, 여덟 단계의 포함/누락 선언, 원본 이벤트 근거 참조가 필요하다.

- 범위는 `scope: request_wall_clock`, 시작 사건은 `request_received`, 종료 사건은 `final_response_delivered`다. 실제로 기록한 요청 접수부터 최종 응답 전달까지의 시간이다. worker 실행 시간 합계나 측정 구간의 최소/최대 시각으로 만들지 않는다.
- UTC의 `Z` 또는 `+00:00`, 소수점 최대 6자리 시각을 사용한다. 시간대가 없는 시각·역전된 구간·잘못된 날짜는 오류다. 결과의 초 단위 값은 정밀도를 유지하는 십진 문자열이다.
- 사용자 후속 입력·선택·도구·승인 대기가 이 구간에 들어 있으면 포함한다. 대기를 임의로 빼거나 이를 순수 모델 계산 속도라고 부르지 않는다. 실행 조건·대기 차이를 평가 기록에 남긴다.
- 두 기록의 시계 출처가 같고 요청 전체의 단계 선언에 missing이 없어야 `routed_minus_direct_seconds`를 계산한다. 한쪽 timing 미제공·missing 단계·다른 clock이면 차이는 null이며 알려진 각 시간은 보존한다. 필수 필드 누락이나 잘못된 scope/시작·종료 사건 값은 입력 오류다. 같은 clock/measurement 조합을 두 방식에 재사용하지 않는다.
- 시간의 단계 선언은 토큰 수집 선언과 별개다. 토큰이 일부 미측정이어도 완전한 요청 시간 기록은 비교할 수 있다. 그때 전체 토큰 절감 판정은 여전히 보류된다.

`declared_comparable`은 선언된 시계·경계·범위가 맞는다는 뜻이다. 해시가 시계 동기화·정확한 이벤트 기록·응답 전달을 인증하지 않는다. 모르는 시각을 예측하거나 코드가 요청 시간을 자동 수집했다는 뜻도 아니다.

## 관측 모델에 적용한 단가 추정

단가표는 `provider`, 3자리 대문자 통화 표기, `unit: per_million_tokens`, 과금 조건을 설명하는 `billing_mode`, 유효 시작/종료, HTTPS 출처·확인 시각·보관한 근거 파일, 모델별 세 단가를 받는다. 실제 적용 조건은 공식 자료를 우선 확인해 입력한다. 통화 환산이나 구독·일괄/우대 요금과의 자동 대응은 하지 않는다.

모델별 `uncached_input`, `cached_input`, `output`은 백만 토큰당 금액을 나타내는 음수가 아닌 십진 **문자열**이다. 정수부 최대 12자리·소수부 최대 12자리이며 float·지수 표기·NaN·음수는 거절한다. 명시적으로 확인한 0 단가는 허용하지만 누락된 단가를 0으로 채우지 않는다.

각 고유 측정의 추정 금액은 다음과 같다.

```text
((입력 - 캐시 입력) × 일반 입력 단가
 + 캐시 입력 × 캐시 입력 단가
 + 출력 × 출력 단가) / 1,000,000
```

캐시 입력은 이미 입력에, 추론 출력은 이미 출력에 포함돼 있으므로 다시 더하지 않는다. float 없이 십진 연산을 사용하고 청구서 단위로 임의 반올림하지 않는다. 단가 유효 범위는 `valid_from` 이상, `valid_until` 미만이며 측정 구간 전체가 그 안에 있어야 한다.

가격을 붙이는 조건:

1. 기존 검사를 통과한 귀속 가능한 고유 측정이어야 한다. 동일 물리 구간은 한 번만 가격을 붙이며 다른 모델/provider 정보가 섞인 중복 참조는 거절한다.
2. metadata의 provider·native 세션 ID/출처·task/dispatch·assignment 위치가 사용량과 일치해야 한다. 해당 turn 시작 경계보다 뒤, assignment보다 앞의 관측 context가 있어야 하며 관측 순서와 최초 context 연결이 맞아야 한다.
3. 그 구간의 관측 모델이 모두 같은 알려진 모델이어야 한다. 요청 모델·역할 기본값·실행환경 적용값으로 실제 모델을 채우지 않는다. 사용량 발생 뒤에만 관측된 모델로 이전 토큰을 가격 계산하지 않는다.
4. 캐시 입력 수치·측정 시작/종료·해당 모델 단가·유효 기간이 확보돼야 한다. 구간 안에서 모델이 바뀌었는데 모델별 토큰이 분리되지 않았다면 평균이나 비율로 나누지 않는다.

현재 조율자 턴 수집 형식에는 모델 context가 없으므로 해당 기록은 토큰 합산은 유지하되 가격은 미확인으로 남긴다. 근거가 빠진 측정을 목록으로 표시하고 알려진 부분 추정치만 보존한다. 어느 방식이든 미측정 단계·가격 미확인이 있으면 전체 `routed_minus_direct_estimated_cost`는 null이다. 모든 정보가 갖춰졌을 때도 상태는 `declared_rate_estimate`, `billed_cost_verified: false`다.

이는 선언한 단가 조건의 **토큰 금액 추정**이다. 실제 청구액·구독 비용·세금·할인·도구/스토리지 등의 다른 비용을 검증한 값이 아니다. 단가표의 공식성·기간·서비스 등급 적용 여부는 파일 해시만으로 인증되지 않는다. 현재 모델 별칭의 요금이나 과금 방식을 추측하지 않는다.

## 검증과 남은 범위

신규 지표 검사 25개를 포함한 관련 회귀 102개를 확인했다. 합성 단가·시간, 실제 수집기의 가상 native 출력으로 캐시/추론 중복 방지·십진 정밀도·누락·가격 유효 기간·세션/배정/context 연결·시간 경계·중복·읽기 전용 CLI를 검사했다. 독립 검토에서 발견한 context 경계와 다른 세션 정보 수용 문제를 수정하고 재검토했다. 단가가 없을 때는 전체 metadata를 보관하지 않고, 단가가 있을 때도 계산에 필요한 검증된 관측 사실만 보관한다.

실제 업무의 요청 시각·공식 단가 근거·전체 수집·청구 정확성·시간/금액 이득은 미검증이다. 이 기능은 실험 때만 명시 호출하며 일반 요청의 상시 라우팅에 추가하지 않는다.
