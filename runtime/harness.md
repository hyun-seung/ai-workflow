# 작업 조율과 인계 준비

하네스는 모델 주위에서 지침·입력·권한·도구·기록·검증을 연결하는 작업 장치다. 이 저장소에서는 공통 계약과 환경 연결을 관리하고, 에이전트 생성·상태·재개는 선택한 환경의 기능을 재사용한다. 별도 범용 실행 엔진을 만드는 것이 기본 목표는 아니다.

## 짧은 운영 흐름

1. 요청한 결과물과 필수 완료 기준을 정한다. 여러 단계·불명확한 요구사항은 [세션·계획 운용](session-practices.md)에 따라 조사와 계획을 먼저 정리한다. 선택적 확인은 시작할 때 분리한다. 작으면 한 담당자로 처리하며, 역할 수를 늘리는 것 자체를 목표로 삼지 않는다.
2. 환경·프로젝트·권한·필요한 의존성을 확인한다. [권한·승인 정책](permission-policy.md)에 따라 실행 경계를 준비하고 남은 예외만 승인 대상으로 보낸다. 같은 세션과 버전에서 이미 읽은 지침·도움말은 재사용한다. 네트워크·소켓·다른 폴더 접근은 실제 허용 범위와 정식 승인 절차를 확인한다.
3. 역할을 나눌 때만 입력과 출력 위치를 점검한다. 다른 작업 공간의 입력은 절대 경로로 지정하고 다음 담당자가 접근할 수 있는지 확인한다. 원래 요구사항과 완료 기준을 함께 전달한다.
4. 위임 뒤에는 네이티브 알림을 기다린다. 중복 알림에 같은 지시를 반복하거나 전체 기록을 매번 읽지 않는다. Orca의 현재 대기 확인은 [환경 가이드](environments/orca.md)를 따른다.
5. 산출물과 검증 근거를 취합한다. 필수 실패는 해결하고 비차단 개선은 모아서 처리하거나 후속으로 남긴다. 변경 영향에 필요한 검증만 실행한다.
6. 요청한 답·소스·실행 방법·보고서의 위치를 사용자에게 전달하고 종료 상태를 알린다. 실행 기록 화면이나 역할별 완료 통지만으로 결과 전달을 대신하지 않는다.

새 폴더·프로젝트·worktree가 필요한 경우 [작업 공간 생성·보관·정리](workspace-lifecycle.md)에 따라 생성 이유와 유지할 산출물·정리 대상을 처음에 정한다. 임시 프로세스 종료와 앱 등록 해제·디스크 삭제는 별도로 확인한다.

로컬 Orca + Codex의 [완료 처리](completion.md)는 명시 세션 기록을 한 번 수집하고, 준비된 정리 계획이 있으면 검증된 임시 폴더를 정리한다. 조율자가 알림 후 호출하는 명령이며 전역 감시 hook은 아니다.

단일 담당자 우선은 항상 순차로 실행한다는 뜻이 아니다. 독립 작업의 병렬 배정 판단은 [제한된 병렬 위임](parallelism.md)을 참고한다. [관리 위임 도구](delegation.md)는 작업마다 명시한 동시·누적 한도를 검사하며, 자동 업무 분해나 직접 CLI까지 통제하지 않는다.

## 다음 작업부터 적용할 운영 기준

다음 항목은 조율자가 지키는 규칙이다. 필드를 적었다고 런타임이 자동으로 제한하지는 않는다. 실제 추가 구현의 우선순위와 완료 기준은 [하네스 개선 목록](harness-roadmap.md)에 모은다.

| 단계 | 실행할 규칙 | 남길 최소 근거 |
| --- | --- | --- |
| 준비 | 기존 환경·의존성·권한 확인 중 바뀐 부분만 확인. Orca + Codex 자동화 운영은 대신 승인 실제 적용 확인 필수 | 버전·유효 모드·준비 결과 참조와 재확인 이유 |
| 배정 | 같은 파일 수정은 한 담당자, 계약 이후 독립 작업은 병렬 후보. 조율자 전체 동시 상한과 요청별 누적 한도를 배정 전에 정함 | 작업별 담당 파일·선행 조건·유효 한도·선택 이유 한 문장 |
| 프로필 | 승인 모드와 모델·effort를 따로 확인. native 기본값을 낮은 프로필로 추정하지 않음 | 요청값/선택 근거/실제값 또는 unknown |
| 인계 | 필수 지침과 짧은 공통 계약, 필요한 원문 위치만 전달. 완료 기록 전체를 다시 입력하지 않음 | 목표·AC·담당 범위·입출력 절대 경로·버전·남은 문제 |
| 검증 | 먼저 대표 정상·실패 사례로 실행 준비 확인. 전체 검사는 영향 범위에 맞춰 한 번 수행 | 실제 명령·결과·실패 분류·재실행 이유 |
| 마감 | 요청 결과부터 전달하고 별도 UI·기록 개선은 후속 작업으로 분리 | 산출물·판정·미검증·프로세스/자원 정리 상태 |

작은 문서 수정·단순 조회는 직접 수행한다. 매번 모든 역할 문서, 전체 세션 기록, 모든 도움말을 읽지 않는다. 이미 읽은 버전과 관련 부분을 재사용하며, 출력이 잘렸다면 누락된 구간만 다시 읽는다. 상위 지침이 요구하는 필수 읽기는 생략하지 않는다.

새 worker는 초기 문맥과 조율 비용이 든다. 권한 검사·짧은 문서 검토만을 위해 연속 생성하지 않는다. 같은 범위의 후속 수정은 적절한 기존 담당자에게 묶고, 다른 업무의 큰 대화가 부담이 된다면 필요한 결과만 참조하는 새 작업을 선택한다. 전체 입력 토큰에는 반복 문맥과 캐시 입력이 포함되므로 고유 자료 크기나 비용으로 바로 해석하지 않는다.

검사 실패는 대상 기능 결함, 테스트 실행기 결함, 환경/권한 실패, 예상한 음성 결과로 구분한다. 수정과 관계없는 전체 matrix·브라우저 검사를 반복하지 않는다. 공통 파서나 공유 계약이 바뀌면 영향을 받는 전체 범위를 다시 확인하고 이유를 남긴다. 화면 작업의 필수 뷰포트·핵심 흐름·접근성 항목은 시작 때 정하며, 미검증 항목을 사후에 선택 사항으로 바꾸지 않는다.

`worker_done`, 업무 AC 통과, 프로세스 종료는 각각 확인한다. 요청 결과가 준비되면 먼저 전달하고, 네이티브 worker의 예약된 자동 회수 상태는 따로 기록한다. 이를 기다리느라 결과 전달을 미루거나 상태를 반복 조회하지 않는다. 작업이 시작한 테스트 서버는 종료하고, 사용자에게 유지할 서비스는 목적·종료 방법을 안내한다.

## 같은 host의 파일 인계 준비

다른 역할의 임시 폴더를 자기 폴더로 착각하는 오류를 줄이기 위한 선택적 도구다. 명시한 입력의 존재·절대 경로·SHA-256을 확인해 작업 본문과 참조 목록을 한 파일로 만든다. 에이전트·모델을 호출하지 않으며 환경 연결, 원격 접근, Markdown에 숨은 파일 참조나 완료 기준을 자동 검증하지 않는다.

```sh
python3 scripts/prepare_handoff.py \
  --project /path/to/project \
  --environment orca \
  --task /path/to/private/task.md \
  --artifact /path/to/private/design-spec.md \
  --output /path/to/private/handoffs/frontend.md
```

상대 입력 경로는 `--project` 기준이다. `--artifact`는 여러 번 지정할 수 있고 자료 본문은 복사하지 않는다. 출력은 템플릿·대상 프로젝트·Git 작업 트리 밖의 비공개 폴더에만 저장한다. 새 폴더는 0700, 파일은 0600이며 기존 파일을 덮어쓰지 않는다. 출력 경로의 심볼릭 링크는 거부한다. 경로·작업 본문도 비공개 정보일 수 있으므로 허용된 담당자에게만 전달한다.

받는 담당자는 host·workspace와 입력 접근 가능 여부를 확인하고, 자신의 허용된 출력 폴더를 사용해 결과의 절대 경로를 반환한다. 파일이 바뀌거나 host가 다르면 참조를 다시 준비한다. 이 파일을 만들었다고 네이티브 worker에 자동 전송되지는 않는다. `workflow.py`의 단독 Codex 실행이나 Orca/Paseo 실행 설정·권한을 변경하지도 않는다.

## 회고와 다음 검증

개선 분석은 매 요청마다 실행하지 않는다. 초기 구성 단계나 기록이 쌓였을 때, 반복 실패·승인 대기·인계 누락이 발생했을 때 수행한다. 실제 요청 내용과 상세 과정은 합의한 비공개 기록 위치에 보관하고 공개 저장소에는 범용 규칙만 반영한다.

다음 대표 작업에서는 완료 기준을 유지한 채 역할 호출 수, 중복 기록 읽기, 승인 대기 종류·횟수, 재작업, 결과 전달 여부를 확인한다. 실제 모델·effort·토큰은 측정 출처가 있을 때만 비교한다. 부분 snapshot의 승인 이벤트 수를 전체 승인 클릭 수로 취급하거나, 미측정을 0으로 바꾸지 않는다.

현재는 조율 지침·로컬 파일 검사와 [승인 대기 상태/알림 처리](approval-waits.md)를 제공한다. 확인된 요청 ID의 중복 억제·전달 확인과 단발성 Orca 상태 조회를 구현했다. Orca 네이티브 위임·결과 반환과 새 Codex worker의 대신 승인 적용은 제한된 실제 실행에서 확인했다. 다른 설치·프로필에서는 해당 범위의 적용을 확인해야 한다. native pending 원본 ID 연결·원본 알림 제어·웹훅 전송·휴대폰 실제 승인·실시간 수집·저장소 어댑터 선택과 개선 전후 효율 비교는 남아 있다.

## 실제 작업에서 확인한 후속 개선

| 우선순위 | 보완할 문제 | 다음 확인 기준 |
| --- | --- | --- |
| 1 | 자식 권한 경로와 반복 승인 알림 | 사전 허용 범위·유효 모드·쓰기 경로를 먼저 대조. 질문/보고 명령의 승인도 구분. 정책 반영·설정 저장·worker 적용·승인 감소를 따로 판정. 남은 대기만 알림 규칙 적용 |
| 2 | 임시 프로젝트·서버가 남음 | 생성 시 유지/임시 구분, 산출물 보관 검증, 프로세스·앱 등록·폴더의 정리 상태를 각각 기록 |
| 3 | 통째로 위임하거나 잘못 분리함 | 같은 수정은 묶고 독립 작업만 병렬 배정. 공통 자료 선별·원문 참조·설정 가능한 상한 적용 |
| 4 | 환경 실패를 각 역할이 반복 발견 | 필요한 도구·의존성·쓰기 경로·localhost 동작을 제한된 smoke로 먼저 확인. 같은 환경의 근거 재사용, 실제 자식 권한이 같다고 추정하지 않음 |
| 5 | 실행기 오류와 대상 기능 실패가 섞임 | 전체 matrix 전에 대표 정상·의도된 실패 경로 확인. 실행 준비/하네스 실패, 예상 오류, 대상 기능 실패를 구분 |
| 6 | 화면 검증 범위가 끝없이 늘어남 | 뷰포트·데이터·주요 흐름·필수 접근성 기준과 추가 확인을 시작에 구분. 설계 검토 결과를 구현자에게 묶어서 전달 |
| 7 | 결과 전달·기록의 상태가 불명확함 | 요청한 답과 산출물을 우선 전달. 실행 성공/업무 판정/정리 상태 분리, 실제 모델·사용량과 미측정 구분 |

표의 기준은 후속 운영·구현 요구다. 명시한 로컬 임시 공간의 정리와 관리 경로의 배정 제한은 구현했으며, 자동 승인 제어·전역 작업 공간 정리·기기 전체 실행 제한은 포함하지 않는다. 실패 원인을 확인한 부분만 검증하고, 수정과 관계없는 전체 회귀나 새 역할 호출을 반복하지 않는다.

현재 반영한 규칙과 아직 만들지 않은 기능은 [하네스 개선 목록](harness-roadmap.md)에서 구분한다. 이 표의 항목마다 새 에이전트를 만들거나 자동으로 후속 개발을 시작하지 않는다.
