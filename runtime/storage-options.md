# 작업 기록의 저장 방식 선택

상태: 2026-11-10 설계 제안. 저장 방식 선택 요구를 반영한 비교이며 모든 어댑터가 구현됐다는 뜻은 아니다. 현재 개발은 SQLite 저장·조회와 공통 JSON 교환형식부터 검증한다. 파일 저장, MongoDB, PostgreSQL 연결의 실제 지원 여부는 각 구현과 테스트로 확인한다.

## 저장 형식과 저장소

사람이 읽는 Markdown 보고서, 프로그램이 읽는 JSON/JSONL 이벤트, 검색·갱신을 담당하는 데이터베이스를 구분한다. MongoDB의 ‘문서’는 Markdown 문서가 아니라 JSON과 유사한 구조의 BSON 데이터 한 건이다.

- Markdown: 결정·이유·결과를 읽고 공유하는 보고서다. 타임라인과 집계에 필요한 모든 필드를 문장만으로 복구하는 기준으로 삼지 않는다.
- JSON/JSONL: 요청·담당자·이벤트의 공통 교환형식이다. JSONL은 한 줄에 JSON 이벤트 한 건을 담는다. 파일 저장 모드의 원문으로 사용하거나 DB 사이에서 내보내고 가져오는 데 쓸 수 있다.
- SQLite/MongoDB/PostgreSQL: 공통 기록을 저장·조회하는 구현 선택이다. JSON 내용을 사용한다는 이유만으로 MongoDB가 필수인 것은 아니다.

어느 저장소를 선택해도 수집 연결, 모델 확인, 승인 이벤트 해석, 판단 근거 요약의 작성은 별도 책임이다. 저장소 선택만으로 누락 없는 자동 수집이 보장되지는 않는다.

## 비교

| 방식 | 장점 | 부담과 한계 | 적합한 경우 |
| --- | --- | --- | --- |
| Markdown 보고서 | 에디터로 바로 읽고 수정·공유하기 쉬움 | 구조 없는 문장만으로 요청·역할·명령을 정확하게 필터링·집계하기 어려움 | 사람의 검토, 인계, 블로그 초안 |
| JSON/JSONL 파일 | DB 서버 불필요, 텍스트로 확인·이동·내보내기 쉬움 | 검색용 파일 스캔/인덱스, 동시 쓰기 조율, 중복·충돌·복구를 파일 어댑터에서 구현해야 함 | 가벼운 템플릿·보관·데이터 교환 |
| SQLite | 별도 DB 서버 없이 로컬 파일에 저장, SQL로 요청·역할·기간별 조회 가능 | 같은 DB의 쓰기는 한 번에 하나, 여러 PC가 DB 파일을 직접 공유하는 구성에 부적합 | 현재처럼 한 PC의 기록 수집·조회 화면 |
| MongoDB | 다양한 이벤트 payload를 문서 형태로 저장, 필드별 검색·인덱스 구성 가능 | 서버/서비스·인증·백업 운영, 관계·일관성 설계와 집계 필요 | 이미 MongoDB를 운영하거나 이벤트 문서 중심의 중앙 수집이 필요한 경우 |
| PostgreSQL | 요청·실행·검증 사이 관계와 SQL 집계, 유연한 JSONB payload를 함께 관리 가능 | 서버/서비스·인증·백업·스키마 변경 운영 | 여러 PC·사용자의 중앙 기록, 역할별 비교·통합 집계 |

SQLite의 로컬 용도와 단일 writer/네트워크 파일 공유 제한은 [공식 사용 가이드](https://www.sqlite.org/whentouse.html)에 근거한다. 여러 에이전트가 있다는 사실만으로 SQLite를 제외하지 않는다. 한 PC의 수집기가 짧은 쓰기를 조율할 수 있는지 실제 부하로 판단한다. WAL에서도 writer는 하나이며 같은 호스트 조건이 있다([WAL 공식 문서](https://www.sqlite.org/wal.html)). 여러 사용자가 웹 API를 통해 하나의 로컬 DB에 접근하는 구성과 여러 PC가 DB 파일 자체를 직접 공유하는 구성은 구분한다.

## MongoDB의 적합성

명령·도구 결과마다 세부 필드가 다른 이벤트를 문서로 보관하는 방식은 이 업무와 잘 맞을 수 있다. 다만 요청 하나의 모든 로그를 한 문서의 배열에 계속 추가하는 구조는 피한다. MongoDB는 문서 크기 제한과 무한히 커지는 배열 문제를 명시한다. 요청과 이벤트를 별도 문서/컬렉션으로 두고 요청 ID·담당자·발생 시각 등으로 연결하는 방식을 검토한다([문서 구조](https://www.mongodb.com/docs/manual/data-modeling/embedding/), [무제한 배열 주의](https://www.mongodb.com/docs/manual/data-modeling/design-antipatterns/unbounded-arrays/)).

현재 요구의 중요한 조회는 ‘어떤 요청의 어떤 실행에 어느 담당자가 참여했고, 어떤 검증과 재작업으로 끝났는가’다. 따라서 관계·집계와 JSON payload를 함께 다루는 PostgreSQL도 자연스러운 중앙 저장소 후보다. JSONB는 JSON 데이터를 저장하고 인덱싱하며, MVCC는 동시 접근의 일관성을 관리한다([JSONB](https://www.postgresql.org/docs/current/datatype-json.html), [동시 접근](https://www.postgresql.org/docs/current/mvcc-intro.html)). PostgreSQL을 향후 중앙 운영의 우선 후보로 제안하는 것은 이 조회 요구에 따른 설계 판단이며, MongoDB가 기능적으로 불가능하다는 의미는 아니다. 두 제품 간 성능 우열은 측정하지 않았다.

## 템플릿에 반영할 경계

공통 수집/정규화 → 공통 요청·담당자·이벤트 계약 → 선택한 저장 어댑터 → 공통 조회 서비스 → 화면/보고서 순서로 분리한다. 모델 요청값/확인값, 미측정 사용량, 원문 출처/해시, 부분 수집 표시, 중복 처리 기준은 저장소를 바꿔도 유지한다.

우선 파일 저장과 SQLite를 선택 가능한 작은 범위로 완성하는 것을 제안한다. Markdown은 공통 기록에서 만드는 보고서 출력으로 취급한다. 파일 모드에서도 화면을 제공할 수 있지만 공통 조회 기능을 실제로 구현·검증해야 한다. JSON import/export만 지원하는 상태를 파일 저장 어댑터 완성으로 표시하지 않는다.

MongoDB/PostgreSQL은 요구가 생긴 뒤 실제 연결 어댑터를 추가한다. 미지원 저장소 설정은 명확한 오류로 알리고, 다른 저장소로 조용히 대체하지 않는다. 저장 방식 설정의 정확한 키/CLI 옵션은 구현 단계에서 정하며 이 문서의 후보를 이미 동작하는 옵션으로 안내하지 않는다.

저장소 이전은 명시적인 export/import로 검증한다. 두 저장소에 동시에 기록할 경우 어느 쪽이 기준인지와 부분 실패 복구를 먼저 정한다. 단순한 설정 변경만으로 기존 데이터가 이동한다고 가정하지 않는다. 원문이 중요한 지시·명령은 정규화된 검색 데이터와 별도로 원문/해시를 보존한다.

현재 권고는 개인 로컬 사용에는 SQLite, 텍스트 파일 보관을 원하는 사용자는 JSON/JSONL 파일 모드, 중앙 운영에는 PostgreSQL을 우선 검토하는 것이다. 이미 MongoDB 운영 기반이 있다면 같은 공통 계약으로 MongoDB를 선택할 수 있다. 실제 기록은 선택한 저장소에서도 비공개 위치에 두며 서버 DB 도입 때는 대상·인증·공개 범위를 명시한다.
