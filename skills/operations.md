# 역할 스킬 운영·인계 가이드

[역할 연결](README.md)과 [운영 준비 완료 기준](rollout.md)의 실무 진입점이다. 역할 문서·설치·실제 사용·품질 검증을 각각 확인한다. 설치별 상태와 근거는 비공개로 보관하고, 공통 저장소에는 범용 절차만 둔다.

## 작업을 시작할 때

대상 프로젝트의 지침과 [실행 환경](../runtime/environments/README.md)을 확인하고 필요한 역할의 문서·적용 스킬 경로를 전달한다. 다른 프로젝트에서 공통 저장소를 자동으로 찾는다고 가정하지 않는다. 아래 경로는 실제 접근 가능한 공통 저장소 경로로 바꾸며 작업 cwd는 대상 프로젝트에 유지한다.

```sh
python3 /path/to/ai-workflow/scripts/skill_catalog.py check
python3 /path/to/ai-workflow/scripts/skill_catalog.py select --role frontend --tag web --tag react-web
python3 /path/to/ai-workflow/scripts/skill_catalog.py select --role backend --tag api
```

| 역할 | 작업에 맞는 선택 | 전달할 결과 |
| --- | --- | --- |
| 조율자 | 필요한 역할·스킬과 고정 버전·범위 결정. 외부 전문 스킬을 억지로 추가하지 않음 | 목표·완료 기준·배정·판정 종합 |
| 설계자 | API 계약 작업이면 `--role architect --tag api` | 요청·응답·오류·호환성·검증 경계 |
| 디자이너 | 기본 후보와 필요 시 `--tag expo` | 화면 기준·상태·기존 시스템과 유지 요소 |
| 프론트엔드 | Web은 `web`/`react-web`, native는 `react-native`/`expo` | 실제 화면·상호작용·API 연동과 자체 검증 |
| 백엔드 | API는 `api`, 원인 조사는 `debugging` | 구현·API 계약·자체 검증·미검증 범위 |
| 검증자 | 기본 후보와 해당 작업의 `web`/`debugging` | 원래 완료 기준별 통과·실패·미검증 |

태그 없는 선택은 해당 역할의 `common` 후보만 반환한다. 빈 목록이 역할 지침 부재나 전체 미설치를 뜻하지 않는다. 태그를 추가해 해당 작업의 후보를 확인한다. 출력의 설치 경로·고정 버전·상태·모드를 확인하고 원문 중 관련 부분을 읽는다. `pilot`은 제한적 시범 사용이 가능하며 `reference-only`는 관련 방법만 참고한다. 설치만으로 사용·통과를 기록하지 않는다.

## 새 설치에서 연결할 때

1. 저장소 지침과 역할별 적용 스킬의 실제 발견 여부를 확인한다. 전역 설정·자동 실행·권한 변경으로 연결을 대신하지 않는다.
2. [설치 절차](README.md#설치와-선택)에 따라 검토한 공식 installer로 고정 원본을 로컬 관리 라이브러리에 배치하고 `check`·해당 역할의 `select`를 확인한다. 다른 설치의 registry·개인 경로를 복사하지 않는다.
3. `skills/catalog.json`은 공통 시작 목록이다. 다른 설치에서 정기 검토로 추가한 후보까지 자동 설치되는 것은 아니다. 필요한 추가 후보는 고정 출처·라이선스·관련 시험을 다시 확인한다.
4. Orca/Paseo에는 역할 문서와 적용 스킬의 절대 경로를 전달하고 실제 접근·실행을 확인한다. `workflow.json`의 단독 Codex 설정이 native 환경의 모델·권한을 자동 대체하지 않는다.
5. 주간 예약이 필요하면 [유지관리 기준](../runtime/skill-maintenance.md#예약과-환경)에 따라 그 설치의 workspace·CLI·installer·보관 위치를 연결한다. 비활성 수동 시험 뒤 활성화하고 실제 실행 이력을 확인한다. 기존 설치의 예약을 다시 만들 필요는 없다.

예약은 [요청문](../templates/skill-review-automation.md)을 매 실행 읽는다. 신규·인기 검색과 기존 버전·호환성 검토 뒤 심층 후보 최대3개, 설치/교체 최대1개를 판단한다. 전체 프레임워크·hook·외부 전송을 자동 도입하지 않는다. 의미 있는 개선이 없으면 기존 버전을 유지한다.

## 결과를 기록하고 화면에서 확인할 때

실제 사용한 원문·고정 버전·방법, 발견·수정·검증과 한계를 기존 결과에 남긴다. 연결된 DB가 있으면 [명시 스킬 사용 계약](../runtime/trace-skills.md)을 사용한다. 기록되지 않은 과거 사용이나 모델·토큰을 추정하지 않는다.

```sh
python3 /path/to/ai-workflow/scripts/trace_viewer.py --db /private/path/workflow.sqlite3 serve --port 8765 --skills-root /path/to/ai-workflow
```

DB는 Git 밖의 승인된 비공개 위치에 둔다. 화면의 역할 카드는 실제 수입한 사용 근거이고, 라이브러리 패널은 설치 상태·검토·변경 이력이다. 검토의 `보류/실패`, 설치의 `시범/활성/비활성/보관`, 사용 기록의 판정은 서로 다르다. 최신 실패를 과거 성공으로 대체하거나 형식이 잘못된 요약을 숨기지 않는다. 조회 화면에는 설치·실행·삭제 권한이 없다.

검증용 가상 DB와 실제 요청 DB를 구분한다. 원래 요청 시각·사용량·실제 프로필이 미확인이면 그대로 남긴다. 업무 결과를 마감할 때는 [마감 계약](../runtime/trace-closeout.md)으로 근거와 제한을 연결한다. 검증 후 작업에서 만든 서버·탭을 정리한다.

## 실패를 확인하고 복구할 때

| 상황 | 확인·조치 |
| --- | --- |
| 설치 원본 무결성 실패 | 사용자 수정·원본·이력을 보존하고 변경 중단. 수정 파일을 덮어써 해시를 맞추지 않음 |
| 검토 중 registry 변경 | 최신 상태를 다시 읽고 영향 검토. 이전 SHA로 강행하거나 다른 실행자의 변경을 덮어쓰지 않음 |
| 원문 URL 조회 실패 | 실패를 보존하고 공식 검색·목차의 현재 경로를 확인. 원문 회복과 SDK/native 실행 검증을 구분 |
| 증거 부족·시험 실패 | 기존 버전 유지와 보류 이유 기록. 다른 버전·역할의 시험을 가져와 승격하지 않음 |
| 새 버전의 재현된 회귀 | 원본 무결성·이력 확인 후 직전 관리 버전으로 rollback. 새 버전도 보존 |
| 중복·부적합 스킬 정리 | 이유·영향 역할·대체를 확인해 disabled. 의존 해소 후 retired로 보관. 필요하면 pilot으로 복원·재검증 |
| 화면에서 조회 실패 | 서버·DB/라이브러리 연결과 원래 HTTP 상태 확인. 유효한 요청의 자료 장애500과 입력400을 구분하고 재조회 |

변경은 `scripts/skill_catalog.py --expected-registry <검토한 SHA256>`에 `status` 또는 `rollback`과 구체적 이유를 전달한다. active 승격에는 해당 버전·역할·태그의 증거 파일도 필요하다. 명령 형식은 [관리 절차](../runtime/skill-maintenance.md#실행과-기록)를 따른다. 신규 항목에 이전 설치가 없다면 rollback 대상이 아니며, 비활성·보관으로 되돌릴 수 있게 관리한다.

관리 도구·조회 계약을 바꿨을 때는 공통 저장소에서 관련 가상 회귀를 실행한다. `test_skill_catalog.py`는 증거·동시 변경 차단과 버전/보관 복구를, `test_trace_skills.py`는 명시 사용·무결성·검토 요약·읽기 전용 API를 확인한다. 외부 installer·실제 후보·브라우저 결과는 별도 근거로 구분한다.

```sh
python3 -m unittest discover -s tests -p 'test_skill_catalog.py' -v
python3 -m unittest discover -s tests -p 'test_trace_skills.py' -v
```

## 초기 구축을 마감할 때

[세 가지 마감 작업](rollout.md)의 실제 근거와 남은 제한을 확인한다. 현재 범위에서 통과했다는 결과를 모든 SDK·native·운영·전체 스킬 품질 인증으로 확대하지 않는다. 이후 주간 후보 검토·업데이트·대체·은퇴는 계속되는 운영이며, 새 후보가 생길 때마다 초기 구축을 다시 미완료로 만들지 않는다.
